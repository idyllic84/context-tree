# 3–6块的独立评估与优化计划（2026-11-19）

处理流程分为8块（1 送达、2 树的组织、3 记忆写入、4 执行context、5 执行者交互、6 工作状态与生命周期、7 回答查询、8 与用户的沟通）。
1、2两块已能独立评估；3–6块的自评（2026-11-19）是：机制大体可用，但评估方法、标签或边界不足以独立优化。本计划先把评估建好，再逐块优化。
结果写进[实现规划](ctm-implementation-plan.zh-CN.md)第7节，块的划分写进[目标与方法](goals-and-method.zh-CN.md) 3.4。

## 共同规则

- **成对**：要比较的各组面对同一批条目。条目（需要的信息、重新交代的内容、应有的约束）先由评判者在**看不到被测输出**的情况下列出，再逐组判断。
  评判者一边列条目、一边看着被测输出判断的做法（2026-11-18的`fresh`、`restate`）不再用于比较。
- **评判者**：opus与terra，只计两人一致的；单一评判者（含早期的grok）的标签只作参考，用到时重标。
- **数据**：用户11-13这周（w1113）用于开发与诊断；用户之后的新数据（`auto_eval.py daily`）与没用过的公开数据作测试；每次修改在没用过的数据上量。
- **指标连到后果**：除了“记下没有、给了没有”，还看它是否到达该到的执行者、是否带进不相干的工作、是否让执行者做对。

## 改进的方法（2026-11-19）

- 能交给模型判断的交给模型，代码只存储、传递、限制资源；说明的内容从“谁读这个输出、拿它做什么、各种错的代价”推出，不从观察到的错例推出，也不写错例里的例子。
- 中间产物按下游的实际使用评：进度总结看后来的执行者真正需要的信息它有没有（`summary_use`），约束看到达，状态看用户之后的行为。
- 找错因的数据与测试的数据分开；同一配置跑两遍看波动；比较版本只用两人一致的判断；评判一致率低的指标（如“是否编造”，40条中常有十几条分歧）分不出相差几条的版本，此时按原理选。
- 一项改进要同时满足：在没用于找错因的数据上有增益，并且能从用途与代价讲通。
