# 相关工作调研

> 2026-10-28 通过LangSearch检索并直接读取公开资料（文档、论文摘要、官方博客）。只记录读到的内容；检索覆盖有限，不据此声称“没有人做过”。
> 比较的依据是[CTM概念模型](ctm-concept-model.zh-CN.md)的目标与设计，不是“别人有就补上”。资料摘录与检索记录保存在私有目录 `research/related-work-ctm2/`。

## 1. 总体结论

没有找到同时具备以下几点的工作：用户只和一个助手对话、多项工作并行且没有session边界；跨时间的Goal／Task工作树；
按工作范围继承与按对象生效的两种约束；查询与任务分开；经由带合同的控制层驱动执行者；用户可在树上纠正。
但每一块都有相近的做法，分散在不同系统里：

| CTM的组成 | 最接近的工作 |
|---|---|
| 助手协调多个执行者、维护计划与进度 | Magentic-One的编排者（任务账本、进度账本）；Anthropic多智能体研究系统的主agent |
| 任务树作为工作记忆 | HiAgent（子目标工作记忆）；Task Memory Engine（任务记忆树） |
| 任务列表、依赖、规划 | Task Master（从PRD生成带依赖的任务）；Kiro specs（requirements／design／tasks） |
| 约束与指令文件 | AGENTS.md、CLAUDE.md、Kiro steering（按文件模式条件加载）、Copilot自定义指令 |
| 人格与对用户的理解 | Letta的persona与human记忆块；Claude Code的自动记忆；Devin的知识建议 |
| 文档与外部化记忆 | Anthropic的产物系统；Manus“把文件系统当作context”；ACE的演进式playbook |
| 时间 | Zep／Graphiti的时间知识图 |
| 多执行者界面 | Vibe Kanban（看板＋每个agent一个工作区）；Claude Squad、Conductor等并行会话工具 |
| 会话内话题树 | Context-Agent、Conversation Tree Architecture（此前已比较，原文已随存档清理） |

CTM可以主张的不同之处，在于这些要素的组合，以及几项具体语义：按服务关系放置任务、两种约束的区分、查询与任务分开、
人格与对用户的理解只给CTM、用户纠正作为权威事件。这一判断受检索覆盖的限制。

## 2. 逐项比较

### 2.1 编排者与主agent

**Magentic-One**（[AutoGen文档](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/magentic-one.html)）：
编排者先制定计划，在“任务账本”（Task Ledger）中维护事实与推测；每一步建立“进度账本”（Progress Ledger），
反思进展并检查任务是否完成，未完成就把子任务分派给某个专门agent，完成后更新进度。
- 相同：一个协调者维护计划与进度，分派执行者，检查完成。
- 不同：它面向单个任务的一次运行，没有跨任务的长期记忆、没有用户对话层和界面，也没有约束的作用范围。
- 可借鉴：进度账本中“是否在推进、是否卡住”的显式自检，对应CTM控制层的“无进展时停止并升级”；卡住时由CTM决定重新规划。

**Anthropic多智能体研究系统**（[工程博客](https://www.anthropic.com/engineering/built-multi-agent-research-system)）：
主agent把计划保存到记忆，以免context超过上限被截断；为子agent写任务描述时，每个子agent需要“目标、输出格式、使用哪些工具和来源的指导、清晰的任务边界”，
否则会重复工作或留下空白；子agent把结果写到文件系统等外部产物中，只把轻量引用交回协调者；接近上限时启用全新context的子agent并做交接。
- 相同：几乎对应CTM的执行合同（目标、产出、边界）、输出约定（长内容进文档、答复只给简要结果）、新执行者靠交接延续。
- 可借鉴：合同里明确写出输出格式和工具或来源指导；按任务复杂度给出投入预算（它按复杂度决定子agent和工具调用数量）。

### 2.2 任务树与任务列表

**HiAgent**（[arXiv 2408.09559](https://arxiv.org/abs/2408.09559)）：以子目标组织单个长任务的工作记忆，子目标完成后概括其观察。
- 相同：完成时把结果概括后留给上层，与CTM的“完成时向上折叠”相近。
- 不同：它管理单个agent在一次长任务内的context；CTM是独立提出的设计，管理用户与多个执行者之间跨时间、跨工作的记忆与context。

**Task Memory Engine**（[arXiv 2504.08525](https://arxiv.org/abs/2504.08525)）：用分层的任务记忆树跟踪执行，每个节点对应一个任务步骤，
存输入、输出、状态和子任务关系，根据“当前活动节点的路径”动态生成提示；并指出将来要支持可复用子步骤、汇合路径和共享依赖（有向无环图）。
- 相同：树节点带状态，按当前节点路径组成context——与CTM“路径上的任务约束进入合同”一致。
- 不同：节点是单次任务内的步骤，没有用户、全局层、约束种类和文档知识。

**Task Master**（[README](https://github.com/eyaltoledano/claude-task-master)）：从PRD生成任务，任务有依赖、子任务、状态，
提供“下一个任务”“展开任务”“复杂度分析”“标签与工作流”等工具供编码agent调用。
- 相同：规划、依赖、可执行顺序。
- 不同：任务列表由用户或agent直接操作，没有一个理解对话的助手，也不记录约束与决定。
- 可借鉴：按复杂度决定是否继续拆分，可作为CTM规划者拆分深度的依据。

**Kiro specs**（[文档](https://kiro.dev/docs/specs/)）：每个规格包含requirements.md（用户故事、验收标准）、design.md（架构、实现考虑）、
tasks.md（可跟踪的离散任务），按“需求 → 设计 → 实施”三阶段推进。
- 相同：交付物与计划写成文档，任务可跟踪。
- 不同：规格以功能为单位、由用户发起，没有跨工作的记忆与助手层。

### 2.3 约束与指令文件

**AGENTS.md**（[agents.md](https://agents.md/)）：给编码agent的项目说明；大型仓库可以在子项目中放嵌套的AGENTS.md，
agent读取目录树中最近的那个，“最近的优先”。**CLAUDE.md**（[Claude Code记忆](https://docs.anthropic.com/en/docs/claude-code/memory)）：
工作目录以上各层的CLAUDE.md在启动时加载，子目录中的按需加载；`.claude/rules/`可以把规则限定到特定文件类型；也可以直接读取AGENTS.md。
**Kiro steering**（[文档](https://kiro.dev/docs/steering/)）：product.md（产品目的、用户、目标）、tech.md、structure.md等项目文件；
可设为始终加载、按文件模式加载（例如只在处理`components/**/*.tsx`时加载）或手动加载；另有用户级的全局steering。
GitHub Copilot也支持项目自定义指令与AGENTS.md（[GitHub文档](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-copilot-overview)）。
- 相同：它们相当于CTM的对象约束与全局偏好——写在项目文件里，随项目走，按目录或文件模式限定范围，越近越具体的优先。
  Kiro的product.md与CTM根节点的整体目标相近，用户级steering与根上的偏好相近。
- 不同：它们都是人维护的静态说明，没有“这项工作怎么做”的任务约束，也没有随工作结束而失效的约束；没有一个助手根据对话写入和维护它们。
- 风险佐证：实践中常见agent不遵守规则文件的报告（例如[Cursor规则被忽略](https://dev.to/olivia_craft/why-cursor-agent-ignores-your-cursorrules-and-rewrites-the-wrong-files-5977)），
  支持CTM在合同中明确要求、并由控制层检查diff。
- 可借鉴：多文件模块的对象约束可以用“按路径模式适用”或“嵌套、最近优先”的方式表达，而不只是一个项目级`ctm.md`。

### 2.4 人格、对用户的理解与知识

**Letta记忆块**（[文档](https://docs.letta.com/guides/agents/memory-blocks)）：persona块存放agent自己的角色与行为方式，human块存放关于用户的关键信息；
记忆块始终在context中、可编辑、可在多个agent间共享，也可以把只读的策略块共享给所有agent。
- 相同：persona与human正对应CTM的人格与对用户的理解。
- 不同：Letta把它们放进agent自己的context；CTM只给CTM自己用，不交给执行者——执行者需要的是由此写出的具体指令。共享只读策略块对应CTM交给执行者的全局约束。

**Devin知识**（[文档](https://docs.devin.ai/product-guides/knowledge)）：每条知识有“触发描述”，当前工作与之相关时被取用；
Devin会根据用户在对话中的反馈自动建议要记住的知识，用户编辑后保存或忽略；知识可按用户启用或停用。
**Claude Code自动记忆**：根据用户的纠正和偏好自己记笔记，与CLAUDE.md一起在每次对话开始时加载。
- 相同：CTM中“推断出的偏好先作为建议、用户认可后生效”的做法与Devin的知识建议一致。
- 可借鉴：给文档和约束写“何时用”的描述，用于检索和让执行者判断是否要读。

**ChatGPT项目记忆**（[TechRadar](https://www.techradar.com/ai-platforms-assistants/chatgpt/chatgpt-project-only-memory-is-live-and-it-might-change-how-you-work-with-ai)）：
可开启“仅项目内记忆”，项目外的记忆对项目内无影响。
- 对比：它用隔离来避免干扰；CTM用全局记忆加作用范围（任务约束沿树、对象约束跟对象）来避免干扰，同时保留跨工作的引用。

### 2.5 外部化记忆与context工程

**Manus**（[博客](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）：把文件系统当作context，内容可丢弃但保留可恢复的引用；
复杂任务中agent维护并逐步勾选一个todo.md，借“复述”把目标留在注意力里；保留出错记录，让模型看到失败；围绕KV缓存命中设计context。
**Context engineering**（[Lance Martin](https://rlancemartin.github.io/2025/06/23/context_engineering)）：把手段归为写出（存到context之外）、选择、压缩、隔离四类。
**ACE**（[arXiv 2510.04618](https://arxiv.org/abs/2510.04618)）：把context当作不断演进的playbook，用增量更新避免改写时的信息坍缩。
- 相同：CTM的“知识在文档里、context里只放路径与要点”“执行者需要时自己读”就是写出与选择；新执行者即隔离。
- 可借鉴：执行者在执行中维护一份对照合同产出的简短清单，控制层据此检查形式完成；知识文档按章节增量更新，不整篇改写。

### 2.6 时间

**Zep／Graphiti**（[arXiv 2501.13956](https://arxiv.org/abs/2501.13956)）：面向agent的时间知识图，事实带有效区间，支持随时间更新。
- 相同：CTM的约束、决定有有效区间，被替换的保留为历史。
- 不同：它以实体与事实为单位；CTM以工作、约束、决定和文档为单位。

### 2.7 多执行者界面

**Vibe Kanban**（[README](https://github.com/BloopAI/vibe-kanban)）：用看板规划工作，准备好后为每个工作建立工作区，agent在其中拥有自己的分支、终端和开发服务器，
完成后审查。Claude Squad、Conductor等工具在一个界面里管理多个并行的agent会话，常用git工作树隔离。
**Jules**（[Google博客](https://blog.google/technology/google-labs/jules/)）：异步执行，完成后给出计划、推理和改动差异。
- 相同：CTM的任务树与执行视图；每个执行者在隔离的工作目录中工作（在CTM中属于执行层面）。
- 不同：这些工具里由用户自己规划、分派和记忆；没有一个助手理解对话、维护跨工作的记忆和约束。

### 2.8 记忆研究的综述与评测

[Memory for Autonomous LLM Agents（2603.07670）](https://arxiv.org/abs/2603.07670)、[Evaluating Memory Structure in LLM Agents（2602.11243）](https://arxiv.org/abs/2602.11243)、
[Agentic Memory（2601.01885）](https://arxiv.org/abs/2601.01885v2)：分别综述记忆机制、比较记忆结构、学习统一管理长短期记忆。
它们以单个agent的记忆为对象，评测多为问答式的回忆能力；与CTM“用户—助手—多个执行者”的结构和“下一步是否做对”的目标不同，可作为评测设计的参考。

### 2.9 常驻的AI同事：Grok Bot与OpenBot（2026-11-24）

**Grok Bot**（SpaceXAI，2026-08发布、11月1.0）闭源。可查的实现材料：从公开安装包0.18.0的`app.asar`还原的源码（社区重建，非官方，按“只还原有实物证据的行为”整理）、
对较新宿主程序编译代码的逐项分析（标明代码可证、推断与未定），与官方文档。
- 它解决的深层问题是**让执行者持续存在**：LLM agent是一次会话，只在运行时存在、装下一个窗口、一次做一件事、依附某台设备。
  它的解法：每个用户一台常驻的云端电脑，agent循环在其上的宿主程序里运行；“说话”与“干活”分开（主对话每轮很短，只回复、记账、分派，
  重活交给看不见的后台执行者，执行者从空白开始、由主对话的模型写简报、没有对用户说话的工具）；每个bot一条长期对话靠摘要延续；
  学到的记忆是关于用户的事实、偏好与规则（每轮记证据、后台合成、要求引用证据、第二个模型复核、用户写的条目受保护）；时间表、事件与子任务完成唤醒它；
  按操作面区分的自动审核、凭据只按引用使用。
- 会话的自动创建与复用：主对话为每条独立的工作流开一个执行者，补充与纠正送进正在运行的那个（`MessageSubagent`），做完的可凭ID恢复（`resume`）；
  分派由主对话的模型在工具循环里判断，依据是它自己的对话窗口与一张待办表（“多任务的记忆”，做完即清）。
- 工作本身是短暂的：执行者的上下文用完即弃，待办做完即清，没有关于每项工作的结构化状态。它押注的是重复、可按职能切开的事务，
  长期保留的是“怎样为这个人做事”。

**OpenBot**（CopilotKit，MIT，开源替代中最受关注的一个）开源的是应用模板（前端、共享定义、各框架适配）；服务端以编译好的镜像发布，
持久对话、记忆与自动学习在单独授权的服务里。与Grok Bot不同：企业多租户；消息交给哪个bot由部署运行的意图路由器决定；每个bot有许多独立的对话；
bot之间的交接按格式写清任务与边界，寻址、落点、深度由部署而不由模型决定；一个对话里的`delegate`开出用户可见、可直接进入的任务线程，
`follow_up`送进本对话已有的任务；bot形成的记忆要用户确认。它的代码注释记录了实测到的分派错误：新交付物被当成补充、停错任务、
对任务报告的回答没送回任务。

**与CTM的关系**：两者都在用户与会遗忘的执行者之间放了一个“声音”。Grok Bot让执行者持续、工作结构短暂；CTM让工作结构持续（以工作为单位、
以用户的话为准、带替换历史，执行context由代码拼装）、执行者可以替换。CTM不借鉴：由模型临场写简报、按职能建多个bot、未经请求主动开工、
多个执行者共用凭据、不可见的自主记忆。可参考的机制按底层能力列在[目标与方法](goals-and-method.zh-CN.md)第6节的顺序里：
执行路由与按操作面授权、凭据引用、证据—合成—复核的记忆流水线、批准变成规则、按唤醒来源区分规则、没人在场时的降级。
OpenBot实测的三类分派错误可作为块1的测试类别。

## 3. 值得采用什么：按CTM的定位与目标判断

CTM的定位是用户唯一对话的助手，管理多项并行工作和多个执行者，记忆不依附于session。判断一项做法值不值得采用，只看它是否推进
[目标与方法](goals-and-method.zh-CN.md)中的六项目标，以及是否与CTM的定位冲突。别人有而我们没有，不构成理由。

### 3.1 理解对：判断用户说的是哪项工作、哪个对象

| 做法 | 来源 | 判断 | 理由 |
|---|---|---|---|
| 消息中显式引用对象（宏、@） | Devin的知识宏 | 采用 | 与界面选择一样是无歧义的定位信号，成本几乎为零；用户想精确时有办法精确，不必靠CTM猜 |
| 知识带“何时用”的触发描述 | Devin | 采用（文档与约束都带） | 检索与执行者自选文档都靠它；CTM的文档数量会持续增长，没有用途描述就难以选准 |
| 人格与用户信息篇幅受限、始终在场 | Letta记忆块 | 采用于CTM自己 | 理解含糊消息时总要用到对用户的理解，按需检索反而可能漏掉；篇幅受限让成本稳定。但只放在CTM的理解context里，不给执行者 |
| 关键词与语义混合检索（如BM25） | Zep等 | 不采用于语义判断 | 与“语义判断只用LLM或向量”的原则冲突。文件路径、提交号这类精确标识的查找属于寻址，可以用 |
| 按项目隔离记忆 | ChatGPT项目记忆 | 不采用 | CTM要跨工作引用决定和结果；干扰由作用范围控制（任务约束沿树、对象约束跟对象） |
| 以话题划分会话内的树 | Context-Agent、CTA | 不采用 | 前次比较已说明：约束按作用的工作与对象生效，而不是按在哪段话题里说的 |

### 3.2 执行对：执行者拿到够用的context并做对

| 做法 | 来源 | 判断 | 理由 |
|---|---|---|---|
| 任务描述写明目标、输出格式、工具与来源指导、边界 | Anthropic | 采用（已写进执行合同） | 它的经验是缺了这些，子agent会重复工作或留下空白，正是CTM执行合同要防止的 |
| 按复杂度给投入预算 | Anthropic | 采用 | 控制层判断“是否该停”需要预算作依据 |
| 执行者维护对照产出的清单 | Manus的todo.md | 采用（执行层约定） | 长执行中让目标留在注意力里；控制层也据此判断形式完成 |
| 保留失败记录 | Manus | 采用：进度里记下失败的尝试和原因 | 新任务或重新激活时执行者是新的，看不到旧session；不记失败，新执行者会重蹈覆辙——这正是“重复不可重复的动作”这类高后果错误的来源 |
| 显式检查“是否在推进”，卡住时重新规划 | Magentic-One进度账本 | 采用：控制层发现卡住时交CTM重新规划 | 自动“继续”的风险就是空转；需要一个停止条件和回到规划的出口 |
| 嵌套的指令文件，最近的优先 | AGENTS.md、CLAUDE.md、Kiro steering | 采用：允许子目录放嵌套的`ctm.md` | 多文件模块的约束范围更准；执行者熟悉这一惯例，漏读的可能更小 |
| 按文件模式条件适用 | Kiro steering、Claude规则 | 采用于`ctm.md`条目 | 一个模块跨目录或只涉及部分文件时需要 |
| 由一个编排者处理全部执行往返 | Magentic-One | 不采用 | 会把执行琐事压到CTM身上；CTM已把这部分分给控制层 |
| 隔离的工作区（分支、终端、开发服务器） | Vibe Kanban、Conductor等 | 属于执行层面 | 概念层只认工作目录；并行修改时由执行层面提供隔离的工作目录 |

### 3.3 记得住：长期之后找回正确的状态

| 做法 | 来源 | 判断 | 理由 |
|---|---|---|---|
| 执行中在里程碑处写出进度 | Anthropic（主agent先把计划存到记忆） | 采用 | CTM的连续性依赖写回；只在结束时写回，执行中断或context到上限就会丢失已完成的工作 |
| 产物写到外部，只传引用 | Anthropic、Manus | 已是CTM的设计 | 印证了“长内容进文档，答复只给简要结果” |
| 增量更新知识，不整篇改写 | ACE | 采用 | 文档会被许多次执行反复修改，整篇改写容易丢掉早先的内容 |
| 事实带有效区间，矛盾时使旧事实失效 | Zep／Graphiti | 已有对应 | CTM的决定与约束已有有效区间与替换；不改用以实体为单位的知识图 |

### 3.4 答得准：知识查询

| 做法 | 来源 | 判断 | 理由 |
|---|---|---|---|
| 结论逐条附出处 | Anthropic的引用环节 | 已有对应 | 查询答复本就要求可追溯 |
| 查询结果保存为可检索记录 | — | 已有 | — |

### 3.5 负担小：用户少纠正、纠正一次就够

| 做法 | 来源 | 判断 | 理由 |
|---|---|---|---|
| 根据用户反馈建议要记住的内容，用户编辑后保存 | Devin、Claude自动记忆 | 采用（补上“编辑后再认可”） | 与CTM“推断先作建议”一致；允许编辑比只能接受或拒绝更省事 |
| 从项目已有说明文件起草约束文件 | Kiro的基础文件生成 | 采用，作为建议 | 新项目上手时减少用户口述；只起草，不直接生效 |
| 大交付按“需求 → 设计 → 任务”组织 | Kiro specs | 作为规划者的一种模板 | 对大的交付有用；但用户大量消息是查询和纠偏，不能变成所有工作的固定流程 |
| 看板视图 | Vibe Kanban | 可选的另一种视图 | 按状态浏览方便；主结构仍是树，因为任务约束要沿树传递，平铺的看板表达不了 |

### 3.6 成本可度量

| 做法 | 来源 | 判断 | 理由 |
|---|---|---|---|
| 以缓存命中率为关键指标，context前部保持稳定 | Manus | 采用 | 执行合同和长期不变的内容放在前面、本次变化的放在后面，几乎不增加复杂度，却直接降低成本与延迟；成本度量中加入缓存命中率 |
| 多agent的token开销显著高于单agent | Anthropic | 作为提醒 | CTM加控制层加执行者的结构同样有开销，必须在评测中计入 |

### 3.7 小结

采用的都落在CTM已有的结构里，没有新增概念：执行合同多了几项内容；控制层多了“卡住时交CTM重新规划”和“里程碑进度”；
进度里记下失败的尝试；`ctm.md`可以嵌套并带路径模式；文档带用途描述并增量更新；对话里可以显式引用；人格与对用户的理解篇幅受限、始终在场；
推断出的记忆可编辑后认可。这些已写进[CTM概念模型](ctm-concept-model.zh-CN.md)。
不采用的，主要因为与CTM的定位冲突：把执行琐事压给CTM、把人格交给执行者、按项目隔离记忆、用关键词做语义判断、以话题或看板代替工作树。
