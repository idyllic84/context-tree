## Current Configuration
- Message flow: seventh round (pointing and objects → candidates → delivery → dispatch → memory). The first version of the flow (understanding→locating→placement→write-back), old prompt versions, and approaches that were not adopted were removed from the code on 2026-11-25; their evaluations are in the [block evaluations](block-evaluation.md) and the git history.
- English conversion (2026-11-25): Code, prompts, and pages were changed to English. Content written by the model for the user (titles, summaries, answers, memory entries) follows the user’s language. Regression checks (research/blk-en, original Chinese version versus English version, same input): for 112 messages in the delivery chain, the delivery method matched in 109, and both method and target matched in 108; two runs of the Chinese version itself matched in 105 (within the range of variation). For 80 memory extraction and replacement cases, both judges agreed that English was better in 13, Chinese was better in 12, and they were comparable in 37. For 40 stop classification cases, the handling matched in all 40. Progress summaries became worse after literal translation (both agreed Chinese was better in 12 and English in 3: the English version put unfinished things in done, and open was often empty). After rewriting the descriptions of open and verified according to the purpose of the two columns, on 40 unused cases Chinese was better in 5, English in 4, and they were comparable in 3; open was nonempty in 21 versus 22. Adopted. Maintenance, structure judgment, Goal organization, query routing, answering, and scope judgment were not tested separately; they are examined through records of actual use.
- Models (selected after measurement by role; see [evolution](evolution.md) 4.5): pointing and objects `gemini-3.8-flash`, delivery and all other calls `gemini-4-argon`, memory `gemini-3.8-flash` (extraction prompt V6—V5 plus what carries object constraints; object rules without a project directory stay on the work they belong to; replacement uses flash for focused comparison, comparison instructions V5: replace only when the old entry as a whole no longer holds), execution control layer `gemini-3.8-flash` (stop classification V2), memory-based answers to user questions and query routing `gemini-3.8-flash` (2026-11-20: equal answer accuracy and routing appropriateness, shorter wait), delivery candidates carry only the most recent result (`deliver.CAND_RESULTS`, 2026-11-20: equal quality, 6.5% less input), progress summary `gemini-4-argon` (instructions V4: state the purpose of the summary and the cost of the two kinds of errors, and analyze what to select from the reply; when waiting on a conditional dependency, also judge the condition), maintenance instructions V11 (analytical; state the purpose, cost, and basis of status judgments, and separately list work that has been inactive for a long time but is still in progress), delivery instructions V17 (V15 plus the `memory` destination: memory operations on CTM and adjustments to CTM’s own practices are not delivered to the executor, 11-24; V15 is V13 plus: the purpose of the previous step’s `after` and the cost of writing it incorrectly or omitting it; state the cost of the two kinds of errors in referencing `uses` as they are; V13 is V11 plus the meaning of the current task: selecting it on the tree switches to it, and selection is more reliable than inference from the most recent turn; V11 is V5’s analytical approach plus: new work references recent queries it will use; new work specifies work or research elsewhere that it will use (`uses`, cross-task references); the consequences of side questions and sending into work, and the cost of judging incorrectly for each; when unsure, treat it as a side question; the most recent results of candidate work include failures and verification status), Goal judgment V5 (argon, analytical; work at the root that is not under a Goal), structure judgment V6 (argon, analytical; group under a Goal or Task by containment, triggered by a delivery signal and by a level where ≥2 items of work have been added during maintenance), new executor context includes the original text of the last 6 turns of conversation, with the resolution of more distant parts reduced according to budget when exceeding 32,000 characters (formerly 24,000); turns whose original text is included in full no longer repeat their progress summaries (concept 3.2); siblings are provided according to concept 5.2 (original text of the last 4 turns for the most recent sibling, 2 turns for the rest, with environment and questions asked); when new work is created, it references sibling constraints that CTM judges also apply to it. Query: retrieve the top 20 records from the entire work line containing the work that raised the question; when a replaced entry is retrieved, include the current entry that replaced it (`recall`).
- CTM does not use the sol series (`common.llm.chat` and `ctm2.model` reject its model names); when sol is used as a judge in an evaluation at the user’s request, set `CONTEXT_TREE_ALLOW_SOL_JUDGE=1` only for that run.
  Models callable only through a pi provider are written as `pi:<provider>/<model>` (windowless subprocess, without tools, session, or context files).
- Evaluation: test every change on unused data (`rotate.py`); annotators and judges are independent of the model under test; no single run exceeds 30 minutes.

## Modules: `src/context_tree/ctm2/`
CTM implemented according to the [CTM concept model](ctm-concept-model.md); `src/context_tree/pilot/` runs it as a local page, with pi sessions as executors.
The code retains only the current version of each workflow and description (plus at most one candidate under evaluation); old versions and approaches that were not adopted are recorded in the evaluation records, and the code is in the version history.

| Module | Responsibility | Concept model |
|---|---|---|
| `store.py` | SQLite memory: entries, edges, events; write, occurrence, and validity intervals and replacement and observation times; sources; “as of a certain time” queries | 3.1, Section 4 |
| `tree.py` | Tree view over the store (`StoreTree`): structural changes leave events through the store; the current state of work as seen by delivery | 3.4 |
| `ref.py` | Pointing and objects: how messages point to work (continuation, reference, naming, time), which objects are named | 5.1 Step 1 |
| `candidates.py` | Find candidates based on pointing: recent work, running executors, pending items and display entries, objects (including spelling errors in identifiers), time | 5.1 Step 2 |
| `deliver.py` | Delivery: where and how each part is delivered (continue, create new, side question, research, control, ask first, CTM records it itself); when nothing is suitable, review all work and judge again | 5.1 Step 3 |
| `remember.py` | Write memory after dispatch: constraints, guidance, decisions, facts, behavior guidance, settings, each attached where it belongs; the replacement step compares each entry with the closest current entry | 5.1 Step 5, 3.5, 3.6, Section 4 |
| `writeback.py` | Write back executor replies: execution evidence, one brief progress entry, long content saved as documents; collect “current entries” for memory | 5.2 Item 6, 3.4 |
| `context.py` | Initial context for a new executor (path and subtree, recently executed siblings, recent conversations, referenced conclusions from elsewhere, approaches not to use again, document and file indexes); increments received by reused sessions; context for research entries; reduce resolution according to budget | Section 2, 3.2, 5.2 |
| `execution.py`、`control.py` | Executor lifecycle (create on first execution, reuse the session thereafter; read-only fork for queries); forwarding; stop classification and completion checks by the execution control layer; escalation of scope violations and lack of progress | 5.2 |
| `progress.py` | Brief progress summary of executor replies (what was done, changes, verification, pending items, failures) | 3.4, 5.2 Item 6 |
| `recall.py`、`query.py` | Answer executor and user queries from memory (provide only current content, marking replaced and questioned items); dispatch read-only execution when memory cannot answer | 5.2 Item 5, 5.3 |
| `relay.py` | Relay: numbered display items (with their owning tasks), pending items | 5.4 |
| `documents.py` | File versions, documents (type, purpose, version, updates by section, obsolete status), object constraint index, behavior guidance documents | 3.5, 3.6 |
| `objectfiles.py` | CTM's own `ctm.md` records: when to write, rewrite or delete upon replacement, proposals and withdrawals of source comments | 3.5, 1.1 |
| `planner.py` | Planner: subtasks as proposals; those already authorized by the user's original words become plans directly; approval | 3.4 |
| `scope.py` | Where constraints go: when the same requirement appears on another branch, lift it, or propose it as an object constraint or global preference; new work references constraints that also apply on siblings | 3.5 |
| `maintain_store.py` | Periodic maintenance: reattach, merge, rename, add ordering, fix statuses, lift constraints, Goal ownership and same-level structure judgment; record inheritance changes caused by reattachment and notify executors | 5.6, 3.4 |
| `root.py` | Root layer: persona, understanding of the user, overall goal, preferences and global constraints, commonly used environments | 3.3 |
| `ui.py`、`views.py` | Propagation of interface changes; pages generated from memory (task metadata, exchange records, documents) | 5.5, 1.2, 3.7 |
| `lifecycle.py` | Status events and valid transitions; dependencies and gating; prerequisites completed→executable; overturned→pending recheck; fold upward on completion | 3.4, Section 4 |
| `model.py` | Model calls (through `common/llm.py`), recording the role and usage of each call | — |
| `pipeline.py` | Main workflow: user message (pointing → candidates → delivery → dispatch → memory → structure judgment → relay); executor reply (evidence, progress, execution control layer, status, escalation and response, open items); periodic maintenance | Section 5 |

Offline tests (all model calls replaced): `tests/test_ctm2_*.py` and `tests/test_pilot*.py`; page check `tests/browser_pilot_ui.py` (see [development notes](development.md)).
