## 0. 为什么需要这份规划

此前按部件逐个实现，概念中互相配合的机制被拆散，单个部件看似可用，组合起来却失效：

| 漏掉的配合 | 后果 |
|---|---|
| 放置只“可选地”给父节点；CTM不能建上级；维护只看节点列表 | 树平或按话题乱挂 → 任务约束沿树传递、工作线最近交流、结果向上折叠都失去依托 |
| 只对约束做替换，决定、状态、环境没有；被否做法不连到替代做法 | 过时说法仍作为现行内容交出 |
| 理解时把环境事实排除在约束之外，又没有任务环境、进度标识、知识文档来存 | 执行context最常见的缺口是缺事实 |
| 没有任务状态与生命周期 | “运行中的执行者”这一定位信号、前置结果交给后继、完成时折叠都无从实现 |
| 没有展示物与待决事项 | “可以，开始吧”“按第二条改”的指代、批准成为决定都无从落地 |

**规则**：
1. 按机制链实现，一步完成一条链上互相依赖的部分，不留下“以后再补”的半截机制；确需推迟的写明推迟什么、缺了它哪些机制会失效、评估时怎样隔离它的影响。
2. 每一步的评估包括四项：本步指标；对下游步骤的影响（用固定的下游探针测）；成本；之前各步不回退。
3. 标准答案不可靠的地方（工作粒度、父子边、替换关系）由用户抽检定标准，不只靠模型标注。

## 1. 机制链：谁影响谁

| 链 | 经过的机制 | 一处出错的下游后果 |
|---|---|---|
| L1 放置与传递 | 理解 → 定位 → 放置（服务关系） → 任务约束沿路径传递 → 执行context的约束与工作线 → 执行 | 挂错：别处约束传进来造成过度收紧，或该有的约束、前置结果、交流原文缺失 |
| L2 写入与时效 | 理解 → 约束／决定／被否做法／环境／进度的写入 → 写入时比对替换 → 执行context与查询只用现行条目 | 过时条目被当作现行；被否做法被重做 |
| L3 生命周期 | 任务状态事件 → 当前任务与运行中执行者信号 → 定位；完成 → 向上折叠 → 父任务进度 → 后继的context | 已完成的任务仍被当作在做；后继拿不到前置结果 |
| L4 执行往返 | 执行合同 → 执行者 → 控制层停顿分类 → CTM用记忆回答或转为待决事项 → 用户 | 停顿都升级给用户，负担大；或CTM答出过时内容 |
| L5 查询与任务 | 理解的查询／任务判定 → 建不建节点 → 树的噪声与粒度；查询记录 → 之后的指代 | 查询建成节点使树变碎；查询结果丢失，转任务时缺依据 |
| L6 展示与指代 | 转述中的编号条目与待决事项 → 用户的短指代 → 写入（批准成为决定、否定成为被否做法） | 批准落不到具体条目，决定缺失 |
| L7 维护 | 写入的消息段与进度 → 维护改挂、建上级、合并 → 约束传递与工作线随之变化 | 改挂后约束传递范围变化未被检查，造成新的过度收紧 |
| L8 知识 | 执行者的长内容与做法 → 文档（用途描述、已核实与未核实、版本） → 执行context的文档索引与查询答复 | 做法和事实只在旧session里，新执行者缺事实 |
| L9 根层 | 对用户的理解、全局偏好与约束、常用环境 → 理解、定位、执行 | 含糊消息理解错；全局约束漏传或传错 |

## 3. 实现步骤

每步都写：覆盖、产出、依赖、下游影响、评估（本步／下游／成本／用户抽检）、推迟。
下游探针固定为三组，每步结束都跑（只跑受影响的部分）：
- **P-loc**：三周材料上已核对的跨任务、留住、新工作决策点（E2），加工作线成对精确度与召回（E4）。
- **P-exec**：80个执行决策点（E5的50个＋工作线反复演变的30个），执行者只写计划，两次匿名评审；记录正确数、错误类别（过度收紧、沿用已推翻的理解、缺事实等）。
- **P-cost**：每条消息、每次派发、每次维护的调用数与token。

### S0 记忆存储

- **覆盖**：3.1全部节点与边（Turn、Segment、Display、Query、Run、Document、对象、FileVersion、Resource；dep、about、serves、produced、involves、uses、supersedes），
  所有节点与边的时间（发生、获知、有效区间、观测时间）与来源；3.6工作目录字段；3.7页面所需的“任务交流记录”可由Segment生成。
- **产出**：可回放的存储（SQLite），带版本；树操作都经由存储，内存树只是视图。
- **下游影响**：所有步骤的数据基础。缺Segment存储会使维护（S4）只能看节点摘要；缺Run会使进度、痕迹优先、文件版本无处挂。
- **评估**：回放三周材料只写不判（用已有的理解输出），检查每条消息、答复都有对应记录且能按节点、时间、来源查回；不需要模型调用。
- **推迟**：L0–L3分辨率的派生（S5做交付时的选择）。

### S1 理解与写入

- **覆盖**：5.1第1步的理解部分与第2步全部；3.5两种约束的种类与**放置层级**（“以后”“所有”向上，拿不准放低）、局部约束触发拆子任务的信号；
  3.6决定（批准、选定、被否）；对展示条目与执行结果的态度落到具体条目（需要S6的展示物，S6之前只处理对上一条答复的态度）；
  长材料存为文档；**用户说出的事实**：环境与位置→任务范围，跨项目的→根上常用环境（执行者答复中的事实不逐条抽取：答复原文存为执行证据，写一条简要进度，长内容存为文档，细节需要时再读，见S6、S7）；
  第4节参照解析（“上次”“修复前”→具体实例）；**写入时的替换**：约束、决定、被否做法、环境与状态与同范围现行条目比较，记下替换关系；
  被否做法连到替代做法；对用户的理解只给CTM。
- **依赖**：S0；放置结果（S2）决定“同一范围”——两步在同一条消息的处理中顺序执行：先理解，再定位，最后写入与替换。
- **下游影响**：约束放置过高→P-exec的过度收紧；替换漏判→沿用已推翻的理解，误判→丢掉仍有效的约束；事实没落位→缺事实；决定抽取过多（现为标准的约3倍）→执行context噪声。
- **评估**：
  - 本步：E1、E3（已有标准）；新增约束放置层级的准确率、替换判断的精确度与召回、事实分类的正确率——这三项没有可靠标准，由用户抽检各约20条定标准。
  - 下游：P-exec中“过度收紧”“沿用已推翻的理解”“缺事实”三类错误的数量，要求不高于现状，目标是缺事实明显下降。
  - 成本：每条消息的理解调用；替换比较只在有新条目且同范围有现行条目时调用。
- **推迟**：对象约束写入文件注释与`ctm.md`（需要真实工作目录，运行时集成时做）；回放中对象约束记入对象索引，交付规则见S5。

### S2 定位与放置

- **覆盖**：5.1定位信号的完整顺序（界面选择与@引用、消息内容、当前任务、最近对话及其中的展示物与待决事项、运行中的执行者、记忆检索＋沿边扩展＋时间权重）；
  3.4位置规则（必须说出服务关系；服务方式；兄弟＋串行；共同上级建为Task级；用户说出目的时建Goal；说不出放根下）；
  拆子任务的局部约束依据（来自S1的信号）；先问还是先做（可逆性）；大树的有界概要。
- **依赖**：S1（理解与局部约束信号）、S0、S3（运行中执行者与状态，S3之前用最近活动近似，评估时注明）。
- **下游影响**：L1整条链；挂错使约束传递错（过度收紧或漏约束）；工作线原文（P-exec最有效的部分）依赖工作线正确；新工作误挂旧节点会把旧进度带进来。
- **评估**：
  - 本步：P-loc全部；**用户抽检约20条父子边与10个根下节点**作为从属关系的标准；新建节点中“说不出服务关系、放在根下”的比例。
  - 下游：在自建树上跑P-exec（不再用标注的树），与标注树上的结果比较；统计因挂错导致约束传入不相干任务的次数。
  - 成本：定位调用的输入随树规模保持有界。
- **推迟**：文档浏览中的页面与段落作为信号（无界面）；回放中界面选择按已有方式模拟（纯推进消息选中目标任务）。

### S3 任务生命周期

- **覆盖**：3.4状态事件（提议、待执行、可执行、执行中、受阻、暂停、报告完成、已核实、放弃、被替换、重新打开）及其时间、原因、来源；
  关系（串行、并行、汇合、条件、二选一）；前置完成→后继可执行；前置结果被推翻→后继待重核；父任务状态；**完成时向上折叠**；
  第4节阶段与时机（事件触发、在途悬置）；跨任务引用的决定改变→引用者待重核（3.6）。
- **依赖**：S0、S1（用户的批准、放弃、完成表态）、S6（执行结果事件；S6之前由历史答复与用户反应推断）。
- **下游影响**：“运行中的执行者”信号（S2）；当前任务的默认；折叠内容进入父任务与后继的执行context（S5）；维护修状态（S4）。
- **评估**：
  - 本步：状态的事后标准（用户随后的话与行为：接受、放弃、重新打开），由两名标注者标注并请用户抽检；折叠内容是否包含结论与“不可行”。
  - 下游：P-loc中依赖“运行中”信号的点；P-exec中需要前置结果的点（新增标注：执行是否需要前置任务的结果）。
- **推迟**：规划者生成的计划与门控（需要真实执行）；回放中只处理用户驱动的状态。

### S4 维护

- **覆盖**：5.6全部：读上次维护以来写入的消息段与进度；合并重复、修父子与先后、补建上级（说出过的目的建Goal，否则Task级）、修状态、改名；
  根下节点在有新记录后复查；**改挂后的约束传递检查**（节点移动会改变它继承的任务约束，变化要列出，必要时提示用户）；尊重用户修改（S9提供修改记录）；
  文档整理（合并、拆分、标出过时，依赖S7）；对象约束迁移（推迟）。
- **依赖**：S0（Segment）、S2、S3、S7。
- **下游影响**：L7；改挂改变约束传递与工作线；维护过度改动会增加用户纠正负担。
- **评估**：
  - 本步：维护前后P-loc的工作线精确度与召回；用户抽检维护建的上级与改挂各约10条。
  - 下游：维护前后P-exec的差异；改挂导致的约束传递变化逐条列出并抽检。
  - 成本：每次维护的输入（只含上次以来的记录与涉及节点）与频率。

### S5 执行context

- **覆盖**：5.2第3条全部：合同（用户原话、授权以原话为准、固定条款）；任务现状（目的、工作目录与运行环境、阶段、进度与验证、待决事项、前置结果）；
  路径上的现行任务约束与决定（含根上的偏好与全局约束；子树例外标出）；同一工作线中被否或被替换的做法单列；进度标出观测时间；工作线最近交流原文；
  相关文档的路径与用途（S7）；用户这次指到的内容；可询问条目；固定顺序；3.2分辨率的选择；对象约束经由固定条款要求执行者读（不在context里按目录整批交出）。
- **依赖**：S1–S4、S7。
- **下游影响**：L4（执行者的问题少不少、CTM能否回答）；P-cost。
- **评估**：P-exec全部；按错误类别对照各上游步骤的改动归因；与原会话完整历史比较；执行者输入token。
- **推迟**：无。

### S6 执行往返、控制层与转述

- **覆盖**：5.2第1、2、4、5、6条（答复到达：原文与痕迹存为证据、一条简要进度、长内容存为文档、用户的反应决定记什么；不逐条抽取事实）：执行形式；生命周期（新建、复用活跃session、转送新消息与新约束、结束条件）；控制层（停顿分类、形式完成、错误与预算、
  越界与约束注释被改、里程碑、只上报六类）；执行者询问由CTM从记忆回答（只给现行内容）；请求转为待决事项；完成与失败写回；控制命令；
  结果处理（Run证据、进度、文件版本、痕迹优先、用户在环时由用户反应决定记什么）；5.4转述与通知（编号条目、待决事项标明任务）；5.1答复。
- **依赖**：S0、S1、S3、S5。
- **下游影响**：展示物与待决事项是S1、S2指代解析的输入（L6）；执行结果是S3状态与S1进度的来源。
- **评估**：
  - E7（已有）；新增E7b：交给CTM的“请用户决定”和“要信息”的停顿，CTM凭记忆能否答对、何时应转问用户（标准来自用户当时的回答）。
  - 展示物：在回放中由历史答复生成编号条目，测“按第二条改”“可以，开始吧”的指代解析（S2的信号）。
  - 下游：用户负担估计（需要用户回答的停顿数）。
- **推迟**：真实执行与痕迹（运行时集成）；回放中执行者不动手。

### S7 知识与文档

- **覆盖**：3.6文档全部：种类、用途描述、已核实与未核实、引用决定编号、单写者、按章节增量更新、过时标记；执行者长内容存为文档；用户贴来的长材料；
  做法类事实写入知识文档；文档索引进入执行context与查询。
- **依赖**：S0、S1、S6。
- **下游影响**：P-exec的缺事实；E8查询答复；维护的文档整理。
- **评估**：P-exec缺事实一类的变化；E8中记忆能回答的比例与正确率。
- **回放局限**：历史中只有文件路径，没有文件内容；以执行者答复中的长内容与CTM从答复整理的做法作为文档内容，评估结论注明这一点。

### S8 查询

- **覆盖**：5.3全部：判定（拿不准按查询，写明“作为查询回答”）、不建节点、记录连到节点或根、记忆或只读执行、观测状态带时间、编号展示、转任务时带上查询结果。
- **依赖**：S1、S5（记忆读取）、S6（只读执行与展示物）、S7。
- **下游影响**：查询记录是之后指代（“按第二条改”）与转任务的输入；查询误判为任务会使树变碎（L5）。

### 第三轮抽检后的修订（树的挂载、约束的边界、session与查询）

**用户的答案与讨论的结论**（已写进概念模型3.4、3.5、5.2、5.3、5.5、5.6与标注说明第五版）：
- 树反映工作本身的构成：父子大体是组成关系，兄弟是同一项工作的并列部分或先后步骤；不机械套用，由CTM结合上下文判断，也可以只是同一项工作在继续；
  新建任务时就考虑把一步步提出的同一项工作归到一个上级；分支的作用之一是约束的隔离与继承，用来检查挂载，但不由约束决定结构；父任务是否完成在需要时判断。
- 约束是必须遵守的限制或规则；做法与计划的指导单列为“指导”（向下继承，不是硬限制）；收尾动作是工作内容；对此前做法的纠正是决定。
  同一要求出现在几个分支上时，对共同上级下所有工作都成立的上移，像对象规则或个人习惯的作为建议交用户认可；上移错了可回退。
- session通常不结束（context满且用户不压缩才结束），放弃只停下执行者；查询fork session回答，结论随下一次转给session；冲突只在用户没表明要改规则时才问；
  CTM只在答案已经明确时代答执行者的选择题。
- 抽检结果：约束放置10项中7项对、3项其实不是约束（指导、工作内容、纠正）；替换10项中9项对（相近但不同的做法被当成替换）。

**实现**：理解第六版（指导单列；只记之后还起作用的指导）、定位第六版、维护第四版（同样的挂载原则；约束上移与回退；上级写具体工作而不是领域）、
`scope.py`（同一要求的去向）、父任务按需判断完成、session与fork、转给session的期间变化（被替换的做法、通知、fork中回答过的查询结论）。离线测试25项通过。

### C块（续）：结构判断——回看已有的结构（2026-11-12）

问题：从三个月历史导入的树几乎只有两层（顶层196个，最大的上级72项子工作）。按代码机制，层级只来自送达（挂到候选中它所属的工作下；“下一步”挂在前一步旁边，
所以从根下开始的一项大工作，后面各步都留在根下）、用户说出的目的、以及维护——而维护只看上次以来的记录。用户分几天、几周提出的同一项更大工作的各部分，
没有机制再看它们：用户反复说过“树是动态的、需要定期修正”“每次新建任务都要考虑最近几个任务是不是一个任务的子任务”，在写概念时被收窄成了“共同上级由维护按窗口建”。

实现（概念3.4、5.6）：一个**结构判断**（`maintain_store.structure`，argon），看树上的一层（某个项目的顶层，或某项工作下面）的全部工作，几项是同一项具体工作的部分时建上级。
它不是每条消息的步骤，由两处触发：送达给出信号（`deliver.PROMPT_V3`的`same_work_as`，或新工作是根下某项工作的下一步），在执行者启动、记忆写完之后调用；
维护时，这批记录涉及的层里，自上次判断以来又加入了至少2项工作的（`changed_levels`，记账，不是语义判断）。工作目录统一写法后再分层（`wd_key`）。

测试（`blockS.py`，标注：opus与grok各自对每一层分组，按“同一项更大的工作”配对，两人不一致的不计）：

|---|---|---|---|
| V1 | 导入的平树，开发8层／测试8层 | 0.39／0.20 | 0.89／0.54 |
| V2（小组优先）、V3（不是分类，写出一个产出） | 开发 | 0.27、0.26 | 0.95、0.93 |
| V4（一组是一项具体工作，不按阶段） | 开发／测试 | 0.90／0.83 | 0.78／0.51 |

  改为维护说明不变（V6）、按“这一层又加入了几项工作”调用结构判断：两次运行中维护自身的改动与V6一致，结构判断建的25个上级grok判20个合理。

### C块（续二）：Goal与挂载（2026-11-12）

用户看了重建的树：最顶层应是Goal，清理之类不是目标，任务间的父子也不是包含关系。核对（`D:/ctm`）：树里没有一个Goal，顶层164个全是Task，其中95个是
没有子节点的一次性小事或调研；导入时按“一段会话里做过的事”建的上级用顿号罗列几件事，子节点混着收尾和顺带的调查；导入与结构判断把工作目录当成硬边界
（498对父子没有一对跨目录），送达却完全看不到候选的工作目录。原因：概念里写了“还没有所属Goal的一次性任务可以先挂在根下”“归纳出的目的建Task级上级，升为Goal须用户认可”，
实际就没有Goal；导入的分工作说明把“一个产出之后接着要另一个产出”算另一项工作，收尾也成了节点。

概念改为：根下只有Goal（长期目标，以后同一目的的工作也挂在它下面；CTM总结的标出来源，用户可改）；Task在Goal下；Task与子任务是包含关系，拆不拆看情况；收尾是继续；
工作目录是判断同一任务、组成部分的参考，不是边界，一个Goal可以跨目录。实现：

- 原context（不附最近对话）：运行期间73条 完整0.22、部分0.40、没有0.38；中位约3,100字符。缺的多出自紧挨着的前几轮、但那几轮属于另一个节点——
  用户在一条对话里交替推进多项工作，新请求常直接接着刚在另一项工作里做完的东西（“把代码提交了”），按树组织的范围（路径、兄弟、叔伯）到不了；兄弟上的多为“部分”（进度总结里没有细节）。

### G块（回答查询）

CTM判为查询、两名标注者也一致标为旁问的消息，在C块运行的记忆上（去掉这一轮之后写入的内容）按当时状态运行`query.handle`（argon），
对照当时真正有现场的执行者的回答与这条对话随后的消息，由grok与opus各自评审（`blockG.py`）。两种错误的代价不同：凭记忆答错会误导用户；不必要的只读执行只是慢一些。

- 原做法（recall找到就用记忆回答，找不到才判断是否只读执行），开发数据w2的32条：凭记忆17条，对6、部分8–10、错1–3；只读15条，必要13–14。
  错的典型：问“某文档里有没有X”（文件现状），凭一条早先“已写入”的记录答“有”，实际没有；部分的多是解释、分析类追问，只拼凑了执行者以前的说法。
- 改为先判断问题的类型（`query.ROUTE`）：问已记录的事（做过什么、定了什么、进度和结果）且记忆回答完整才凭记忆；问文件、日志、运行状态、外部数据的现状，
  或要解释、分析、推理的，派发只读执行（相关工作session的只读分支），记忆的回答作为线索。开发数据：凭记忆4条，对3–4、部分0–1、错0；只读28条，必要18–19、不必要9–10（两名评审一致30/32）。
- 留出数据（w3，10-15至10-18，33条，两名评审一致29–30/33）：原做法凭记忆15条，对3–4、部分10–12、错0–1；只读18条。新做法凭记忆0条（这段时间几乎都是技术与解释类提问），只读33条，必要25–28、不必要5–8，计划能回答问题32–33。采用ROUTE。
