# 任务型对话的上下文树形管理系统

## 核心创意

为大模型Agent对话设计一套基于**任务演化逻辑**的上下文管理系统，用树形结构组织用户输入和系统输出，根据意图分类动态提取相关上下文。

### 与传统方案的区别

- **不是RAG**: 不涉及领域知识检索，专注任务型对话
- **不是语义检索**: 不依赖embedding相似度，而是基于任务关系
- **不是简单窗口**: 不是滑动窗口或全量历史，而是结构化提取

### 应用场景

用户与Agent的典型交互模式：
- 提出新任务
- 基于输出提出修改要求
- 调整约束条件
- 切换方案
- 依赖前序任务的结果
- 目标演化

## 用户意图的多维分类体系

### 维度1: 任务操作类型 (Task Operation)
- **NEW**: 提出新任务
- **REFINE**: 细化当前任务
- **EXTEND**: 扩展任务范围
- **FIX**: 修复问题
- **ROLLBACK**: 回退到之前状态
- **REPLACE**: 替换方案

### 维度2: 目标稳定性 (Goal Stability)
- **GOAL_NEW**: 全新目标
- **GOAL_STABLE**: 目标不变
- **GOAL_PIVOT**: 目标转向
- **GOAL_EXPAND**: 目标扩展

### 维度3: 依赖关系 (Dependency)
- **INDEPENDENT**: 独立任务
- **SEQUENTIAL**: 依赖前序结果
- **PARALLEL**: 同级任务
- **CONDITIONAL**: 条件依赖

### 维度4: 约束变化 (Constraint Change)
- **ADD_CONSTRAINT**: 增加限制
- **RELAX_CONSTRAINT**: 放松限制
- **CHANGE_CONSTRAINT**: 修改限制
- **NO_CONSTRAINT**: 无约束变化

### 维度5: 作用域 (Scope)
- **CURRENT**: 仅当前任务
- **SIBLING**: 影响同级任务
- **SUBTREE**: 影响整个子树
- **GLOBAL**: 全局影响

### 维度6: 反馈类型 (Feedback Type)
- **APPROVAL**: 确认满意
- **CLARIFICATION**: 澄清需求
- **CORRECTION**: 纠正理解
- **EVALUATION**: 评估结果

## 树形结构设计

### 节点的核心属性

**基础信息**
- 节点ID、内容、角色(user/agent)、时间戳

**意图分类**
- 6个维度的多维分类结果

**任务状态**
- 当前目标描述
- 累积的约束条件列表
- 任务状态 (pending/in_progress/completed/abandoned)
- 产出的artifacts (文件、代码、结果)

**树结构关系**
- 父节点、子节点列表
- 深度、分支标签
- 活跃状态

### 树的组织原则

**分支类型**
- **Main Branch**: 目标稳定的任务演化链
- **Refinement Branch**: 局部优化分支
- **Alternative Branch**: 方案切换分支
- **Dependency Branch**: 下游依赖链
- **Parallel Branch**: 同级并行任务

**约束的继承机制**
- 子节点继承父节点的目标和约束
- 支持约束的增加、放松、修改、覆盖
- 向上遍历路径时累积有效约束

**节点插入策略**
根据意图分类决定新节点的挂载位置：
- NEW + GOAL_NEW → Root的新分支
- REFINE/EXTEND + GOAL_STABLE → Current的子节点
- REPLACE + GOAL_PIVOT → Current的同级分支
- ROLLBACK → 历史节点的子节点

### 实际示例结构

```
Session Root
├─ Goal Branch 1: "写个数据处理脚本"
│  ├─ Task Node: 初始需求
│  ├─ Agent Response: 初版代码
│  ├─ Refinement: "改成异步"
│  │  ├─ Agent: 异步版本
│  │  └─ Extend: "加进度条"
│  │     └─ Agent: 最终版本
│  └─ Fix Branch: "处理空文件bug"
│     └─ Agent: 修复后代码
├─ Goal Branch 2: "分析数据结果" [依赖Branch 1]
│  ├─ Task Node: 新任务
│  └─ Agent: 分析代码
└─ Goal Branch 3: "改用API获取" [目标转向]
   └─ Alternative方案
```

## 上下文提取算法

### 分层提取策略

**Layer 0: 必选核心 (CRITICAL优先级)**
- 当前用户输入
- 该目标分支的根节点 (目标定义)
- 最近一次agent输出 (用户通常基于此提要求)

**Layer 1: 路径继承 (HIGH优先级)**
- 从当前节点到目标根节点的路径
- 提取模式：摘要 (目标、约束、关键决策)
- 不包含完整对话内容

**Layer 2: 依赖节点 (HIGH优先级)**
- SEQUENTIAL依赖的源节点
- 包含依赖任务的输出结果

**Layer 3: 同目标的兄弟节点 (MEDIUM优先级)**
- 适用于REPLACE/ROLLBACK操作
- 提取已完成的备选方案摘要

**Layer 4: 受影响节点 (MEDIUM优先级)**
- 根据SCOPE维度确定影响范围
- 提取需要同步更新的节点

**Layer 5: 产物引用 (HIGH优先级)**
- 解析用户提到的artifacts引用
- 查找生成该artifact的源节点

### 上下文压缩策略

当token超预算时的降级方案：
1. **降级模式**: 完整内容 → 摘要 → 元数据
2. **移除低优先级**: 删除MEDIUM优先级项
3. **合并同类节点**: 同分支连续节点合并
4. **时间衰减**: 远古节点只保留元数据

### 节点的表示模式

- **full**: 完整内容
- **summary**: 摘要 (目标+约束+结果)
- **metadata**: 元数据 (仅 "曾要求过X")

## 关键技术挑战

### 1. 意图分类的准确性
**问题**: 6个维度组合空间大，需要准确识别

**可能方案**:
- 小模型(GPT-4-mini)做few-shot分类
- 规则引擎 + 关键词匹配
- 训练专门的意图分类器
- 初期简化为3个核心维度

### 2. 指代消解
**问题**: "前面那个"、"用这个"、"改成那样"等模糊引用

**可能方案**:
- 维护最近N个实体(任务/文件/代码块)的引用表
- NER提取artifact名称
- 距离优先 + 类型匹配
- 利用上下文推断

### 3. 树的剪枝与归档
**问题**: 长对话导致树过大

**可能方案**:
- 标记abandoned分支降低优先级
- 归档completed且无后续引用的分支
- 保留骨架节点(目标+约束)
- 设置树的深度/节点数上限

### 4. 约束冲突检测
**问题**: 新约束可能与历史约束冲突

**可能方案**:
- 维护约束的语义表示
- 规则引擎检测逻辑冲突
- 提示用户确认
- 自动覆盖策略

### 5. 分支爆炸
**问题**: 用户频繁切换主题导致树过于复杂

**可能方案**:
- 智能合并短时间内的相同主题
- 设置分支数量限制
- 引导用户明确当前活跃分支
- 自动归档不活跃分支

### 6. ROLLBACK的精确定位
**问题**: 用户说"还是用之前的"，如何准确找到目标节点

**可能方案**:
- 分析用户描述的特征
- 展示最近的分支点供用户选择
- 维护"检查点"节点
- 时间窗口 + 语义匹配

### 7. 依赖关系的推断
**问题**: 隐式依赖难以识别

**可能方案**:
- 分析用户输入中的指代词
- 检测artifact的引用关系
- 追踪数据流
- 主动询问用户确认

## 优势与劣势

### 相比传统方案的优势
- **精准性**: 基于任务逻辑而非语义相似度
- **可解释性**: 树结构清晰可视化
- **灵活性**: 支持复杂的任务演化模式
- **效率**: 避免无关历史消耗token

### 潜在劣势
- **实现复杂度**: 需要意图识别、树操作、指代消解等多个模块
- **冷启动**: 前几轮对话树结构不完整
- **分类准确性**: 依赖意图分类的质量
- **维护成本**: 树结构需要持续维护和优化

### 高度相关的学术研究

#### Context-Agent（ICLR 2026 审稿中）— 最直接验证

把多轮对话历史建模为**动态树结构**而非线性序列，支持多分支对话，结合 RAG 做结构感知的上下文选择。引入 NTM（Non-linear Task Multi-turn）benchmark。**优于主流上下文管理方法，同时减少 token 使用。**

与本设计的核心思路一致：树形结构 + 按结构剪枝 + 非线性对话分支。

#### [Context Folding](https://arxiv.org/)（ByteDance/CMU/Stanford, 2025）— 剪枝验证

Agent 分支处理子任务，完成后**折叠**中间步骤为摘要。用 FoldGRPO（RL）训练 agent 学习何时分支、何时折叠。**实现 10× 更小的 active context**，在 BrowseComp-Plus 和 SWE-Bench 上匹配或优于 baseline。

本设计的"分层提取 + 降级模式"本质就是折叠。Context Folding 提供了量化验证。

#### [HiAgent](https://aclanthology.org/)（ACL 2025）— 分层工作记忆

用 subgoal 作为记忆分块，完成的 subgoal 摘要后剪掉详细的 action-observation 对。**成功率 2×，context -35%，时间 -19.4%。** 含 trajectory retrieval module。

与本设计的方案 4（双层树）高度一致——目标层稳定，执行层可剪枝。

#### [HierTOD](https://www.vldb.org/)（VLDB 2025 DASH Workshop）— 企业层次任务

复杂任务分解为层次化工作流树，用层次有限状态机管理。统一 slot-filling 和 step-by-step guidance。面向企业级任务导向对话。

#### [CoDial](https://arxiv.org/)（2025）— 对话流图

用异构有向图（CHIEF）表示对话流，将专家知识转换为可执行对话逻辑。支持 zero-shot 对话系统规范。

#### 对话管理综述（2025）

~42% 的近期系统采用层次化目标追踪，~63% 使用 frame-based 架构。树形/层次化方法正在成为主流。

### Tree vs Graph：学术对比研究

2024-2025 年有多篇论文直接对比了树和图两种结构在上下文管理中的表现：

#### 关键对比数据

| 论文 | 结论 | 数据 |
|------|------|------|
| [MemTree (Accenture 2024)](https://arxiv.org/html/2410.14052v2/) | 树在在线/实时场景优于图 | 接近离线 GraphRAG 性能，**时序推理任务上超越所有方法** |
| [GraphReader (Alibaba 2024)](https://arxiv.org/html/2406.14550) | 图在多跳推理上优于树 | 4K context 图结构**超越 GPT-4-128K** |
| [TaciTree (2025)](https://openreview.net/pdf?id=33MLSumRMZ) | 树在个性化对话中高效 | 检索准确率 **+30%**，token **-40~60%** |
| [KAPA (ACL 2025)](https://preview.aclanthology.org/orcids-2024/2025.findings-acl.319.pdf) | 树在多领域意图理解中高效 | 检索复杂度 **O(log n) vs O(n)** |

#### 核心权衡

| 维度 | 树结构 | 图结构 |
|------|--------|--------|
| **表达力** | 层次化，仅父子关系 | 任意关系，多跳 |
| **检索复杂度** | O(log n)，子树跳过 | 更高，需遍历策略 |
| **实时更新** | 高效（在线插入） | 通常需离线重建 |
| **多跳推理** | 弱（跨分支链接缺失） | 强（捕获远距依赖） |
| **可解释性** | 高（路径清晰） | 低（关系复杂） |
| **时序推理** | 出人意料地强（MemTree） | 不确定 |
| **实现复杂度** | 中等 | 高 |

#### 2025 学术共识

> **树是图的特例**——树适合层次化索引和实时场景，图适合复杂关联推理。**混合方案**（图存储 + 树索引/可视化）是最佳实践。
>
> — MemOS（Memory Operating System）的做法：底层用图存储丰富关系，上层转换为树用于导航和可视化。

#### 对本设计的启示

本设计选择树形结构用于 **session 内的任务管理和上下文剪枝**——这是树的强项（层次化目标分解、子树跳过、O(log n) 检索）。

而 [companion 设计](claude-code-companion.md) 选择图结构（GraphRAG）用于 **跨 session 的知识存储和关联检索**——这是图的强项（多跳推理、跨 agent 关联、任意关系）。

两者是互补的：

```
Session 内（实时，在线）        跨 Session（离线，积累）
    树形结构                      知识图谱
    任务分解 + 剪枝               实体 + 关系 + 检索
    O(log n) 快速定位              多跳关联推理
         │                            │
         └──── session 结束 ──────────→│
               树的关键节点            提取为图谱节点
               (目标/决策/约束)         (decision/topic/term)
```

| 特性 | 学术研究（通用对话） | 本设计（coding agent 专用） |
|------|------------------|--------------------------|
| 意图分类 | 通用对话意图 | **6 维分类体系**（task_op + goal_stability + dependency + constraint + scope + feedback） |
| Agent 主动分解 | 大多是用户驱动 | **Agent 生成子任务**（规划/依赖发现/迭代建议）的三种场景和三种策略 |
| 约束继承 | 少见 | **子节点继承父节点约束**，支持增/减/改/覆盖 |
| 方案切换 | 少见 | **Alternative Branch + REPLACE/ROLLBACK** |
| 跨任务协调 | 通用图结构 | **父任务协调机制**——子任务独立，父任务负责 context 分发和输出整合 |

# 第二轮讨论：树形结构的本质和剪枝策略

## 核心澄清

### 树形结构的价值
- **不是为了表达所有语义关系**（依赖、引用等可以运行时解析）
- **核心价值在于剪枝效率**：通过树的层级关系快速排除无关节点
- **节点代表任务，子节点代表子任务**
- **子任务之间相互独立**，不存在子任务A的输出直接给子任务B
- **父任务负责协调**：持有完整context，分发给子任务

### 关键原则

1. **子任务的定义**：能够达成任务目标的独立步骤（不局限于传统的"任务分解"）
2. **子任务的独立性**：每个子任务只与父任务交互，不需要知道其他子任务
3. **父子协调机制**：
   - 子任务的输出返回给父任务
   - 父任务整合所有子任务的结果
   - 父任务决定给每个子任务什么context
4. **跨分支引用**：运行时动态解析，不需要在节点上预先记录

## 六种树形组织方案对比

### 方案1: 按目标层级组织（层次分解）

```
Root: "构建数据处理系统"
├─ Task A: "数据读取" (goal_level=1)
│  ├─ A1: "CSV解析" (goal_level=2)
│  │  ├─ A1.1: "处理编码" (goal_level=3)
│  │  └─ A1.2: "处理空值" (goal_level=3)
│  └─ A2: "数据验证" (goal_level=2)
└─ Task B: "数据分析" (goal_level=1)
   └─ B1: "统计计算" (goal_level=2)
```

**剪枝策略**：
- 处理A1.1时，只需向上回溯到A→Root的目标链
- 完全跳过A2、B及其子树

**可行性评估**：
- ✅ **剪枝效果好**：兄弟子树完全隔离
- ✅ **语义清晰**：树结构反映目标分解
- ❌ **目标变化难处理**：用户"其实我想要X"会破坏层级
- ❌ **跨任务引用复杂**：B1引用A2的输出需要向上回溯再横向查找

---

### 方案2: 按时间顺序组织（会话树）

```
Session Root
├─ [1] User: 初始需求
├─ [2] Agent: 初步方案
├─ [3] User: 修改A
│  └─ [4] Agent: 执行修改A
├─ [5] User: 修改B
│  └─ [6] Agent: 执行修改B
└─ [7] User: 新任务
   └─ [8] Agent: 处理新任务
```

**剪枝策略**：
- 处理[7]时，判断[7]与[1-6]的相关性
- 如果是新目标，跳过[1-6]
- 如果是延续，包含最近的相关节点

**可行性评估**：
- ✅ **简单**：按时间append即可
- ✅ **完整**：保留所有历史
- ❌ **剪枝效果差**：需要遍历判断相关性
- ❌ **结构不清晰**：看不出任务关系

---

### 方案3: 目标-步骤混合树（推荐）

```
Goal: "数据处理脚本"
├─ Step1: "基础实现"
│  └─ output: v1代码
├─ Step2: "加参数解析"  [extends Step1]
│  └─ output: v2代码
├─ Step3: "改成异步"  [extends Step2]
│  └─ output: v3代码
└─ Step4: "换原生Python"  [replaces Step3, alternative to Step1-3]
   └─ output: v4代码
```

**剪枝策略**：
- Step4是替换方案，标记[replaces Step3]
- 处理Step4时，只需Goal的定义，不需要Step1-3的细节
- 可以选择性包含被替换方案作为"反例"

**可行性评估**：
- ✅ **剪枝灵活**：通过标签控制包含范围
- ✅ **支持版本切换**：替换、回退自然表达
- ⚠️ **需要准确的关系标注**：extends/replaces/refines
- ❌ **平铺结构**：所有Step是兄弟，无法表达子步骤

---

### 方案4: 双层树（目标树 + 执行树）

```
=== 目标树 ===
Goal: "数据处理"
├─ SubGoal A: "数据读取"
└─ SubGoal B: "数据分析"

=== 执行树（挂在SubGoal A下）===
SubGoal A
├─ Execution 1: pandas方案 [abandoned]
│  ├─ Conv[1,2,3]
│  └─ output: pandas代码
└─ Execution 2: 原生Python [active]
   ├─ Conv[4,5,6]
   └─ output: 原生代码
```

**剪枝策略**：
- 目标树稳定，很少变化
- 执行树记录尝试过程，只保留active分支
- 处理SubGoal B时，只需SubGoal A的output，不需要Execution细节

**可行性评估**：
- ✅ **剪枝效果极好**：abandoned执行分支完全隔离
- ✅ **语义分离**：目标 vs 实现过程
- ⚠️ **复杂度高**：维护两棵树
- ❌ **目标树何时创建新节点不明确**

---

### 方案5: 焦点栈 + 平铺节点

```
=== 平铺节点序列 ===
[1] Goal: "数据处理"
[2] Step: "基础实现"
[3] Step: "加参数"
[4] Goal: "结果分析"  ← 新目标
[5] Step: "统计计算"

=== 焦点栈（运行时维护）===
处理[5]时:
Stack: [1] → [4] → [5]
只需这条路径上的节点
```

**剪枝策略**：
- 不用树，用栈记录当前焦点路径
- 新输入时判断：
  - 延续当前焦点 → push到栈
  - 新目标 → pop到合适层级，push新目标
  - 回退 → pop回到指定节点

**可行性评估**：
- ✅ **极简**：不需要维护复杂树结构
- ✅ **剪枝天然**：栈外的节点自动被排除
- ❌ **无法表达并行任务**
- ❌ **历史分支丢失**，无法回溯对比

---

### 方案6: 标签式树（松散层级）

```
所有节点都挂在Root下（扁平），用标签建立关系：

[1] tags: [goal:data-process, level:0]
[2] tags: [goal:data-process, step:impl, level:1, parent:1]
[3] tags: [goal:data-process, step:args, level:1, parent:1, depends:2]
[4] tags: [goal:analysis, level:0]  ← 新目标
[5] tags: [goal:analysis, step:stats, level:1, parent:4, ref:2]
```

**剪枝策略**：
- 查询[5]时，通过标签过滤：
  - goal=analysis → [4,5]
  - ref=2 → [2]
- 完全跳过goal=data-process的其他节点

**可行性评估**：
- ✅ **灵活**：任意添加关系标签
- ✅ **支持多维度查询**
- ⚠️ **标签准确性依赖分类质量**
- ❌ **不是真正的树**，失去树的结构化优势

## 节点创建的核心算法

### 判断同级子任务 vs 深层子任务

**核心问题**：需要理解当前目标以及用户输入对目标的改变程度

#### 判断维度1: 目标作用域变化

```
当前目标: "实现CSV读取功能"

输入A: "加上错误处理"
→ 作用域: 仍然是"CSV读取"
→ 判断: 同级子任务

输入B: "错误处理要分三种情况：文件不存在、格式错误、权限问题"
→ 作用域: "错误处理"（更细粒度）
→ 判断: 如果刚创建了"错误处理"子任务，这是它的子任务
```

**量化方法**：
- 提取输入中的名词短语作为作用域
- 比较当前任务的goal和输入的作用域
- 如果作用域缩小 → 深层子任务
- 如果作用域平级 → 同级子任务

#### 判断维度2: 实现的完整性

```
当前任务状态: 基础CSV读取已完成

输入A: "加上参数解析"
→ 是新的独立功能点
→ 判断: 同级子任务（并列的功能）

输入B: "参数解析中的文件路径参数要支持相对路径"
→ 是"参数解析"的细化
→ 判断: 子任务的子任务
```

**量化方法**：
- 如果输入是"加上X"、"还要X" → 同级
- 如果输入是"其中X"、"X要Y" → 深层

#### 判断维度3: 依赖深度

```
Task A: "数据读取"
├─ A1: "CSV解析"
└─ A2: "数据验证"

输入: "验证时要检查每列的数据类型"
→ 明确是A2的细化
→ 判断: A2的子任务
```

**量化方法**：
- 解析输入中的指代关系
- 如果明确提到某个已存在的子任务 → 它的子任务
- 否则 → 当前任务的同级子任务

### 目标变化的分类

| 变化类型 | 示例 | 节点操作 |
|---------|------|---------|
| **扩展** | "加上X功能" | 当前任务的新子任务 |
| **细化** | "X功能中要Y" | 当前子任务的子任务 |
| **修改** | "改成Y" | 当前子任务的兄弟（替换） |
| **回退** | "还是用之前的" | 回到历史节点 |
| **转向** | "不做A了，做B" | 父任务的新子任务 |
| **独立** | "另外做X" | 根级新任务 |

## Agent主动生成子任务

### Agent生成子任务的三种场景

#### 场景1: 任务规划阶段

```
User: 构建一个数据处理系统

Agent分析后:
→ 创建子任务: "数据读取"
→ 创建子任务: "数据清洗"
→ 创建子任务: "数据输出"

树结构:
Root: "数据处理系统"
├─ [Agent生成] "数据读取"
├─ [Agent生成] "数据清洗"
└─ [Agent生成] "数据输出"
```

**剪枝效果**：
- Agent明确了任务边界
- 后续只需激活相关子任务
- 未涉及的子任务自动被剪枝

#### 场景2: 执行中发现依赖

```
User: 实现用户认证

Agent开始实现时发现:
→ 需要先有"数据库连接"
→ 需要"密码加密工具"

Agent创建子任务:
├─ [Agent生成] "数据库连接" [前置依赖]
├─ [Agent生成] "密码加密" [前置依赖]
└─ [User请求] "用户认证逻辑" [depends on above]
```

**可行性分析**：
- ✅ Agent发现隐式依赖，显式化
- ✅ 用户不需要考虑技术细节
- ⚠️ Agent可能过度拆分，导致树过深

#### 场景3: 迭代细化

```
User: 写个脚本

Agent: [提供v1代码]
     同时创建改进建议子任务:
     ├─ [Agent建议] "添加错误处理" [optional]
     ├─ [Agent建议] "添加日志" [optional]
     └─ [Agent建议] "添加单元测试" [optional]

User可以选择激活哪些建议
```

**可行性分析**：
- ✅ 引导用户完善任务
- ✅ 预先构建任务树，加速后续迭代
- ❌ 可能与用户意图不符

### Agent生成子任务的三种策略

#### 策略A: 预规划（前置分解）

- Agent一次性分解任务
- 逐个执行子任务
- **剪枝效果**: ✅ 明确，所有子任务一目了然；❌ 不灵活，用户可能改变计划

#### 策略B: 惰性分解（按需创建）

- 执行中发现需要子任务时才创建
- **剪枝效果**: ✅ 灵活，根据实际需要创建；⚠️ 树结构不完整，回溯时可能缺失信息

#### 策略C: 显式询问

- Agent询问用户是否分解任务
- 用户同意后创建子任务
- **剪枝效果**: ✅ 用户参与决策；❌ 增加交互轮次

## 推荐的混合方案

### 核心架构：目标-步骤混合树 + Agent按需分解

```
Root Goal
├─ SubGoal A [User提出]
│  ├─ Step A1 [Agent分解]
│  │  ├─ Step A1.1 [User细化]
│  │  └─ Step A1.2 [User细化]
│  └─ Step A2 [Agent分解]
└─ SubGoal B [User提出]
   └─ Step B1 [User/Agent]
```

### 节点类型

- **Goal节点**：用户提出的目标，较稳定
- **Step节点**：执行步骤，可能被替换/修改

### 创建规则

1. 用户新目标 → 创建Goal节点
2. Agent分解任务 → 创建Step节点（标记agent生成）
3. 用户细化 → 判断作用域，决定同级/深层

### 剪枝规则

1. Goal节点向上回溯到Root
2. 同Goal下的其他Step完全跳过
3. abandoned的Step分支剪掉
4. Agent生成但未激活的Step剪掉

### 父任务的协调机制

**父任务职责**：
- 收集相关context
- 决定给子任务什么context
- 整合子任务的输出
- 维护任务状态

**上下文传递**：
```python
def extract_context_for_subtask(subtask):
    context = []

    # 1. 父任务分配的context（已经是精选的）
    context.append(subtask.assigned_context)

    # 2. 向上回溯到root，收集目标和约束
    current = subtask.parent
    while current:
        context.append({
            "goal": current.goal,
            "constraints": current.constraints
        })
        current = current.parent

    # 3. 完全不需要看兄弟任务！（父任务已经决定了该给什么）

    return context
```

**剪枝威力**：
```
Task A: "数据处理系统"
├─ Subtask A1: "CSV读取" [10轮对话]
├─ Subtask A2: "数据清洗" [15轮对话]
└─ Subtask A3: "结果输出" [5轮对话]  ← 当前任务

处理A3时，剪掉了A1和A2的25轮对话！
```

## 关键设计决策

### 1. 跨任务引用的处理

**问题**：如果SubGoal B需要引用SubGoal A的输出？

**方案A**：父任务负责跨任务协调
```python
RootTask.prepare_context_for_subtask():
    context = {
        "goal": self.goal,
        "external_input": resolve_reference("上面脚本", global_tree)
    }
```

**方案B**：不创建独立任务，而是同一父任务下的子任务
```
RootTask: "数据处理"
├─ Subtask1: 基础实现
├─ Subtask2: 参数解析
├─ Subtask3: 异步改造
└─ Subtask4: "结果分析"  ← 不是新根任务！
```

**倾向**：方案B，因为有依赖关系说明是同一大任务的步骤

### 2. 几乎每次用户输入都创建新子任务

按照"子任务=独立步骤"的理解：
- "加参数解析" = 一个子任务
- "改成异步" = 一个子任务
- "修复bug" = 一个子任务
- "换个方案" = 一个兄弟子任务

**例外情况**：
- 纯澄清/确认："好的"、"对"
- 补充信息："CSV格式的"（回答Agent追问）

### 3. 节点状态管理

```python
class TaskNode:
    type: "goal" | "step"
    creator: "user" | "agent"
    status: "planned" | "active" | "completed" | "abandoned"

    goal_scope: str  # 用于判断层级
    depends_on: List[NodeId]  # 运行时依赖，不是树结构
```
