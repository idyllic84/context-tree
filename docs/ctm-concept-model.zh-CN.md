# CTM概念模型

> CTM（Context Tree Manager）是用户与执行agent之间的助手。用户只和CTM对话；CTM以任务树和有版本的文档作为长期记忆，
> 回答查询，经由执行控制层派发并驱动执行者，并为每次执行准备小而够用的context。
> 目标与方法见[目标与方法](goals-and-method.zh-CN.md)。旧版本（v1：隐形CTM，输入只有消息与记忆）保存在
> [演进过程](evolution.zh-CN.md)第4节（存档已清理）。
> 本文按“世界模型 → 记忆 → 运行 → 规则 → 场景推演 → 待验证问题”组织；第7节的推演是各项设计的依据。

## 1. 世界模型

### 1.1 参与者与分层

| 参与者 | 是什么 | 关系 |
|---|---|---|
| 用户 | 同时推进多项工作的人，像对一个助手那样说话 | 唯一的意图来源，权威最高 |
| CTM | 助手：理解、记忆、路由、回答查询、转述；为每次执行写执行合同；维护自己放在对象旁的记录（`ctm.md`） | — |
| 执行控制层 | CTM与执行者之间的驱动层 | 按执行合同把执行者驱动到完成，只把需要CTM的事交上来 |
| 执行者 | 单次LLM调用、subagent或session，形式由CTM选择 | 默认不与用户直接对话（以后再考虑） |
| 外部世界 | 工作目录及其中的文件、服务、云资源 | 由执行者操作（CTM只写它自己的`ctm.md`），CTM观测其变化 |

**各自的事**：用户的工作——代码、文档、提交，外部世界里的一切改动——由执行者做；执行者只拿到用户的原话和context，CTM不在其中夹带自己的事。
CTM自己的事——它的记忆、放在对象旁的`ctm.md`记录、对话中的答复与提议——由CTM自己做，不交给执行者。用户对CTM说的话（要它记住的偏好与规则、对它或所有执行者以后做法的调整）也是CTM自己的事，不送给执行者。
原因（2026-11-23真实试用）：CTM把写对象规则夹带进同目录执行者的输入，`ctm.md`随那项工作的提交进了PR；用户让CTM“全局记住”的话被送给执行者，执行者去改了它自己的全局配置文件。两处都是把CTM自己的事和用户的工作混在了一起。

### 1.2 界面

| 界面 | 内容 |
|---|---|
| 对话 | 用户与CTM的一条连续对话，多项工作交错进行。只保留最近一定数量的轮次，用于理解短指代。CTM写给用户的每条消息都可被指代：待决事项带编号并标明所属任务。用户也可以在消息中显式引用节点、文档或条目（例如@某任务）。对话有一个**当前任务**，显示在界面上：默认是用户上一次交流所针对的任务，用户在树上选中另一个节点即切换；执行者从别的任务发来的报告不改变它 |
| 任务树 | CTM认为的工作节点：标题、状态、进展、关系、正在执行的标记、提议中的子任务、任务约束。用户可以移动、合并、拆分、改名、改状态、改挂消息、移动约束、改约束种类 |
| 执行视图 | 各任务的执行者：所属节点、形式、状态（工作中、等待、空闲）、正在做的动作。每个任务记着它当前的执行者session（另有已结束的和查询用的只读副本），需要时只读查看完整执行记录；执行者的答复是给CTM的，对话里只有CTM的转述（5.4）。用户不直接在执行者session里说话：那样说的话不进记忆，也会与CTM同时写一个session |
| 查询面板 | 只用于显示，没有输入框。用户在对话中提问，被CTM判定为查询的段，答复显示在这里：全面、标出处和时间，历史与被替换的说法明确标为历史；保留以往的查询答复供查看 |
| 文档浏览 | 树节点的页面（任务元数据、任务交流记录）、知识文档、项目文档；版本历史与差异；双向链接（3.7） |

“打破session”指记忆和工作不再绑定在某个agent session上，而不是取消对话。

### 1.3 CTM能知道什么

能知道：对话的最近一段（含自己说过的话和展示过的东西）与已写入记忆的一切；用户在界面上的修改与选择；
执行者的输出与执行痕迹；工作目录与资源的观测；时间。不能知道：用户没说出的意图，没被观测到的外部变化。

### 1.4 用户怎样说话（前提，待用户习惯研究核对）

- 接着对话里刚说的事时，用户用短指代（“可以”“这个”“改吧”）——对话最近一段就是上下文。
- 转到另一项工作时，用户多半会说出工作名、对象（项目、服务、文件）、产物（文档、PR、报告）或时间（“昨天那个”）；历史里新会话的第一条消息约六成单凭自己就能定位，其余靠当时所在的目录等环境——在CTM里对应在树上选中节点。“继续”“现在呢”“进度如何”这类没有指向的推进、控制和状态询问总是针对当前任务（CTM一定有用户最后交流的那项工作）：用户要转到别的任务再说“继续”，会先选中那个任务。
- 用户说的“第二条”“那个方案”多半指向CTM刚展示过的内容，或文档浏览中正在看的段落。
- 用户会把日志、报错、代码或文档整段贴进来：材料本身不是指令，指认工作的是其中的对象（服务、文件、报错类型）和随附的那句话。
- 用户写的标识（文件名、PR号、分支、区域）可能有拼写错误。
- 几项工作并行时，“刚才”可以隔很多轮：回放中约5%的消息所指的工作在20轮以前；回到几天前的工作时，用户多半说出对象。

## 2. 四种context

| context | 读者 | 用途 | 原则 |
|---|---|---|---|
| 理解context | CTM | 定下这条消息送到哪里、记下什么（5.1） | 指向与对象：消息与最近两轮；送达：候选工作的现状与它们周围的树、最近的对话、界面选择、待决事项与展示条目、运行中的执行者；记忆：送达的位置及这条路径上、对象与全局的现行条目 |
| 执行context | 执行者 | 正确地做下一步 | 执行合同＋小的初始内容，缺什么由执行者询问或自己读；只含当前有效的；不含人格与对用户的理解 |
| 查询答复 | 用户 | 了解、核对、决定 | 全面、可追溯；历史标为历史 |
| 纠正输入 | CTM | 修正自己的组织 | 用户在树、约束、决定、文档上的修改 |

执行context与查询答复读者不同、目的不同，分别构造、分别评估。

## 3. 记忆

长期记忆在树和文档里。每条消息到达时就写入，对话窗口滑过后不丢东西，也不需要压缩对话。

### 3.1 节点与边

| 类 | 节点 | 作用 |
|---|---|---|
| 工作 | 根、Goal、Task／subTask | 单父树：根 → Goal → Task → subTask |
| 约束与决定 | 任务约束（在树节点上）、Decision、Rejected | 简短条目，来自用户或经用户采纳；权威在这里，不在文档里 |
| 对象约束 | 对象文件中的约束注释，或所在目录及其上级目录中`ctm.md`的条目（`ctm.md`只留在本地，不进版本库） | 对象自身的规则；CTM只建索引 |
| 对话 | Turn（用户或CTM的消息）、Segment（用户消息的分段）、Display（CTM展示过的东西，条目带编号） | 最近窗口用于理解；消息段挂到所属节点，长期保存 |
| 查询 | Query（问题、答复、出处、观察到的状态） | 不进入树；连到相关节点 |
| 执行 | Run（一个执行者：执行合同、初始context、经控制层的往返、输出与痕迹） | 证据；执行过的任务对应一个session（通常一直可继续），查询用它的fork |
| 知识与对象 | Document、对象（文件、模块或组件、接口、服务）、FileVersion、Resource | 知识写在文档里，随版本演进；版本连到产生它的Run与任务 |

主要的边：根→child→Goal→child→Task→child→Task；Task→dep(串行、汇合、条件、二选一)→Task；
Segment／Query→about→节点；Display→about→节点／决定；Run→serves→Task；Run→produced→FileVersion；
Task→involves→对象；对象→contains→文件；Decision→detailedIn→Document；Task→uses→Decision／Document／调研／别处的结果，以及CTM判断也适用于它的兄弟约束（跨任务引用）；
Decision→supersedes→旧决定；FileVersion→prev→FileVersion。所有节点和边带时间（第4节），并记录来源：用户、CTM、执行者、规划者、维护、界面修改。

### 3.2 分辨率

节点按L0句柄、L1卡片、L2详情、L3原文分层表示，交付时为每个节点选一层；L1由L2派生。执行context有篇幅预算，超过时先降低离当前工作最远的部分的分辨率；当前任务、约束与决定和用户的原话不降。

### 3.3 根节点（全局层）

不属于任何Goal、长期有效的内容放在根上。用户可以在界面上查看和修改，每次修改留版本。

| 内容 | 例子 | 谁用 |
|---|---|---|
| 助手设定（人格） | 角色与职责；原则（如实说明不确定、不越权、出错先认）；沟通方式；主动程度；风险取向 | 只给CTM |
| 对用户的理解 | 角色与专长；工作方式（并行推进、短指代、偏好最小改动、自己审diff）；常见意图模式；过去常被纠正之处；委托习惯 | 只给CTM：用于理解含糊消息、决定转述详略、判断该问什么、把合同范围写准 |
| 整体目标与优先级 | 这段时间最重要的几件事、先后、不能牺牲的东西 | CTM用于理解、排列待办、冲突取舍、提建议；不产生授权 |
| 用户偏好与全局约束 | “不要用PowerShell”“文档用中文写” | 即根上的任务约束，向下继承，CTM与执行者都遵守 |
| 常用环境 | 机器、常用工作目录、账号与用途 | 执行的工作位置来源；易变的带观测时间 |

- 不属于任何Goal的对话（对CTM的要求、偏好、整体目标的讨论、跨目标的问题）挂在根上，形成根的交流记录。
- **来源分开**：用户设定的与CTM推断的分开记录；推断出的偏好、目标变化先作为建议出现，用户认可后生效。
- **对用户的理解**是推断：每条记依据、把握程度和时间，用户可见可改，与用户新的表达矛盾时以新的为准；只限工作相关的方面；
  初始内容来自历史协作中总结的用户习惯（[用户行为模式](user-behavior-patterns.zh-CN.md)）。它不能压过用户的明确表达，也不替用户做决定。
- **始终在场、篇幅有限**：人格与对用户的理解篇幅受限，始终放在CTM的理解context中，不靠检索取用；超出篇幅时由CTM提议合并或删去把握低的条目。
- **稳定**：人格的修改是明确的事件；整体目标长期没有对应活动或工作明显转向时，CTM提出确认而不自行改写。
- 整体目标说明“为什么、什么优先”；Goal是根的子节点、一项具体的目的，可以服务于多个整体目标（用连接表示）。

### 3.4 任务树

- **判据**：Goal／Task必须有明确产出（文档、代码、报告、配置等交付物），或改变某种资源的状态（文件、服务、环境、数据）。
  只为了知道点什么的请求是查询（5.3），不建节点。
- **调研类工作**：到外部去收集信息（网上资料、别的项目、论文与文档）的调研，目的是知道，产出是一份长篇结论，写成知识文档（不是交付物）。用户没有说明它为哪项工作服务、
  或内容与现有工作无关时，它不挂在任务树上，而是像查询一样记在查询列表里；但它可以跨几轮继续，有自己的要求、执行session和结论文档。以后某项任务用到它时记下引用，
  那项任务的context带上它的结论；用户后来说出它为哪项工作服务、或维护看出它确实是某项工作的一部分时，再把它挂进树里。
  问的是项目本身（代码、session历史、做过的事、现状）的，是查询（5.3），先找树中相关的任务，用它的session的fork来回答，不是调研条目。
  接着之前某一步继续的调研，跟着它的前一项：前一项是调研条目就继续它，前一项是某项任务就属于那项工作。这些都由CTM看情景判断。
- **Goal是长期目标**：根下面只有Goal，每个Task都挂在它服务的Goal下。用户说出的目的（“我想做一个……”“现在要做……”）在说出时建为Goal；用户没有说出时，CTM从这次的请求总结它服务的长期目标：例如“转写这三个文件”是Task，它的Goal是“转写文件”，以后的转写请求继续挂在这个Goal下。总结时问自己：以后同一目的的工作能不能挂进来？Goal不是这一次的请求本身，也不是项目或工作目录（工作目录是工作的地点，一个Goal可以跨几个工作目录）。CTM总结的Goal标为“CTM总结”，用户可以在树上改名、合并、移动或确认。
- **Task的来源**：用户、CTM归纳、规划者（CTM调用的规划agent）、执行者（执行中开出的支线）、用户在界面上新建。
  规划者与执行者开出的节点先是提议，用户批准或属于已授权范围后才成为计划。大的交付可以由规划者按“需求 → 设计 → 实施任务”的文档组织，这只是规划的一种模板，不是所有工作的固定流程。
  用户要求先做规划、或明确给出要分步完成的大交付时，送达在这项新工作上标出“需要规划”，CTM调用规划者；其余情况由执行者在执行中自己安排步骤。一次性的请求也是挂在它服务的Goal下的Task。
- **位置**：树反映工作本身的构成。Goal下的Task是这个目标下的具体工作；Task与子任务之间是包含关系：子任务是父任务的一部分，子任务都完成了父任务才完成；兄弟是同一项工作的并列部分或先后步骤（先后用串行关系连起来）。要不要拆子任务、按步骤拆（确认是哪三个文件／转写／总结）还是按部分拆（转写A／B／C），看情况。
  这只是大方向，不机械套用：同一类动作（推送、验证、写文档、排查）在不同上下文里可能是兄弟、子任务，也可能就是同一项工作在继续。挂在哪里由CTM结合上下文判断，判断时考虑：
  - **要不要建节点**：有能单独验收的产出，或有只属于它的要求（局部约束）时才单独成为节点；同一项工作的继续（例如提交之后“推送并建PR”）可以只是这项工作的一条进度；执行之后的收尾（清理临时产物、关闭服务、切换或删除分支）是这项工作的继续，不建节点；同一次执行中的中间步骤不拆。
    执行这项工作时发现的、属于它本身没做好或没做完的问题，用户说“继续解决”时，是这项工作的继续，记在进度里，不新建节点；某个问题有了只属于它的要求、要单独验收、
    或要放到以后或另一路单独推进时，再成为子任务。调查、查询或审查发现了问题、要修复并交出新产出的，是新的工作，按组成关系挂。
    子任务是父任务当前执行的直接延续时，在父任务的session里做（复用它的session）。
  - **同一项、子任务还是兄弟**：看这项工作在上下文里怎样构成，而不是看动作类型。例如“分析接入方案”与“按方案实现”是同一项工作的两个并列部分，不是后者挂在前者下面。工作目录是重要的参考：同一项任务的工作通常在同一个地方，在不同工作目录里的多半是不同的任务（一项任务也可能跨两个仓库）；它只是参考，不是边界，由判断的一方结合内容来看。
  - **归到Goal与同一个上级**：用户常把同一项工作一步一步、隔几天甚至几周提出来（用户的原话：每次新建任务时都要考虑最近几个任务是不是其实是一个任务的子任务；树是动态的，需要定期修正）。所以新建任务时，CTM就考虑它服务哪个Goal、它和最近的哪几项是不是同一项任务的部分；之后还要定期回看已有的结构，不只看新写入的记录：把还不在Goal下的工作归到它服务的Goal下，同一个目标的几个Goal合并，同一层里同一项任务的几个部分归到一个上级任务下。上级任务是一项具体的任务，说得出它的一个产出；按时期、阶段或领域归组会把约束和现场扩散到只是同处一个阶段的工作。同一批工作常有几种都合理的组织方式，没有唯一的答案，树也随时会调整；选哪种，看哪种对树的用处（约束的继承、执行者看到的现场、用户在树上找到自己的事）更有益。
  - **用约束的后果检查**：分支节点的作用之一是约束的隔离与继承，但结构不由约束决定。定下位置前检查一下：这样挂，已有的约束会不会传进不相干的工作、该有的约束会不会到不了；会的话多半是挂错了，重新判断。
  父节点的候选来自送达时找来的工作与已有的Goal（5.1）；新工作至少挂在它服务的Goal下，说不出属于Goal下哪项工作的就挂在Goal下，以后再整理。用户在一项工作中途提出的新要求，常是被它引出来的——为了它、因为它的结果、顺着它想到的——即使要的东西更通用；也可能只是想起了另一件事。所以判断位置时要分析这项要求为什么在这时提出、和当前工作是什么关系：当前任务不是新工作的默认上级，但起因是判断的重要依据；起因在当前工作、产出又更通用的，放在它下面或单独成一项都可能合理。CTM记下每项工作是在做哪项工作时提出的，以后整理结构时也用得上。深度不设上限。树是动态的，随新的工作与要求调整；每次调整都列出各节点继承的约束有什么变化，并告知受影响的执行者。
- **关系**：串行、并行、汇合、条件、二选一，可混合、可修订；树上的顺序不表示执行顺序。
- **状态**由事件推动并记录时间、原因、来源：提议、待执行、可执行、执行中、受阻、暂停、完成（依据只有执行者的报告）、已核实（完成且有验证痕迹）、放弃、被替换、重新打开；两种完成都是CTM按情景判断的任务状态，区别只在依据，用户认可也是依据之一。
  执行者报告“这次的请求做完了”只记在执行记录上，不等于任务完成：任务往往还有用户接下来的追问和修改。任务是否完成由CTM看情景判断（用户的认可、目的是否达到、之后有没有接着做）。
  前置完成使后继可执行；前置结果被推翻时后继待重核。父任务是否完成在需要时判断（用户问进度、有后继依赖它、要向上折叠结果）：看子任务是否都已完成，并对照父任务的目的——子任务是一步步加进来的，可能还没覆盖目的的全部。
- **任务的内容**只有三样：目标与范围（含工作目录与运行环境：继续这项工作要知道的地址、集群、端口、密钥所在位置、相关目录；以及用户对做法与计划的指导，例如“注意参考之前各步解决了什么、怎样解决的”“测试要广”，它像约束一样向下继承、随任务结束，但交给执行者时标为指导，不是硬限制）、约束与决定、进度（每次执行一条简要总结：做了什么（含产生的版本、分支、PR号等）、更新了哪些文档和文件、验证情况（有痕迹还是自述）、未决事项，以及试过但失败的做法和原因——新执行者看不到旧session，不记下失败就会重蹈覆辙；每条带写入时间，是当时的状态），外加状态、待决事项、在途执行和相关文档的连接。知识不放在任务里：怎样运行、测试、查询之类的做法由执行者按输出约定写进文档；多个项目共用的环境写到根上的常用环境。**CTM不从执行者的答复中逐条抽取事实**：答复原文作为执行证据保存，CTM只写那一条简要总结，答复里仍有长篇内容时整体存为文档；其余细节留在文档和执行证据中，需要时检索或由执行者自己读；哪些内容成为决定、被否方案或待决事项，由用户对转述的反应决定（5.2第6条）。用户在消息里说出的环境、位置等事实写进任务的范围，与约束、决定一样在写入时记下时间与替换关系；执行者的报告不能替换用户说出的约束和决定。
- **完成时向上折叠**：结果与结论（含“不可行”）写入父任务并交给后继。
- **结果向上折叠，任务约束向下传递**，都沿同一棵树。

### 3.5 约束

| | 任务约束 | 对象约束 |
|---|---|---|
| 说的是什么 | 这项工作怎么做：范围、方法、流程、节奏（“这次只改新增代码”“先不做测试”） | 对象本身必须满足的规则：设计约定、接口契约、不变式（“transport不能暴露采样率参数”） |
| 存放 | 树节点：根、Goal或Task | 对象文件中的约束注释；不能加注释的对象（JSON配置、生成文件、二进制）和多文件模块写在包含它的最近一级目录的`ctm.md`，整个项目的写在根目录的`ctm.md`（`ctm.md`只留在本地，不进版本库）；工作目录之外的对象写在CTM文档区的对象说明里 |
| 对谁有效 | 该节点及其所有后代 | 任何涉及该对象的工作，不论属于哪个Goal |
| 寿命 | 随节点结束；只对一条消息有效的随下一条消息结束 | 直到被用户的决定修改或撤销；没有注释就是没有约束 |
| 怎样到达执行者 | 从根到当前任务路径上的任务约束进入执行合同 | 执行合同要求执行者改文件前查看文件中的约束注释，以及从项目根目录到该文件所在目录路径上的全部`ctm.md` |

**什么是约束**：约束是对工作的限制或必须遵守的规则（范围、方法与工具、流程与节奏、格式，例如“使用az cli”“列表很长，要分批拉取”“请连续多轮推进”）。以下不是约束：
对做法与计划的指导（“注意参考之前各步解决了什么”“测试要广”），属于任务的目标与范围，标为指导；收尾动作或开始下一步的要求（“清理临时产物，只留关键记录”），是这次的工作内容；
对此前做法的纠正（“先只分析用户消息，agent回复先用LLM总结”），是决定，替换被纠正的做法。

**任务约束**：越深、越具体、越新的优先；子节点上与上级相反的约束只有来自用户的明确表达才成立，记为这棵子树上的例外并标出。
放在哪个节点由CTM根据用户的话判断（“以后”“所有”“这个功能都”是向上的信号）；拿不准时放低不放高——
放得过高会把约束带进不相干的工作造成过度收紧，放得过低最多是别处缺一条，用户一提或在树上上移即可修正。
**约束的上移与回退**：同一要求出现在几个分支上时，CTM判断它的去向：对共同上级下的所有工作都成立的，上移到共同上级；说的是某个对象的，提议改为对象约束；对所有工作都成立的个人习惯，提议作为根上的偏好。
移到根上的、改为对象约束的，都是建议，用户认可后才生效。上移错了可以回退：用户说某处不适用时，记为那棵子树上的例外，或放回下层。
**新工作加入一层时**：用户常在做其中一项时说出对更大的整件事的要求（对同一个产物的规定、这类工作每次都要遵守的做法），它挂在那一项上，后来加入的兄弟收不到，用户只好再说一遍。所以新工作建立时，若同层的兄弟上有约束，CTM判断其中哪些也适用于这项新工作，引用给它（交给执行者时注明是CTM的判断、原是哪项工作的要求），兄弟和这一层的其余工作不动；用户可以在树上去掉。把这些约束上移到共同上级、或把几项归到一个新上级下，会把它们带给只是同处一层的工作，评估中误伤多，不这样做（实现规划第7节“约束到达的后果”）。

**对象约束**：约束和对象在一起，执行者打开对象就读到约束，人看文件也能看到，修改随版本留下历史，离开CTM也成立。
- **嵌套的`ctm.md`**：任何目录都可以有`ctm.md`，作用于该目录及其子目录中的文件；从项目根目录到文件所在目录路径上的各级`ctm.md`都适用，条目相互矛盾时离文件最近的优先（与AGENTS.md的惯例一致，执行者熟悉）。较近的`ctm.md`与上级相反的条目同样只能来自用户的决定，并注明是对上级的例外。一个模块跨几个目录、或只涉及目录中部分文件时，条目可以写明适用的路径模式。
- 用户说出一条对象约束时CTM记下它。在它所属的那项工作进行期间，它经由对话交给这项工作的执行者——执行者有用户的原话，之后的细化与替换也随对话转去；
  在需要从文件读到它的执行者开始之前——另一项工作的执行者、或一个新的会话进入这个目录时——或它所属的工作结束时，CTM自己把它写进包含该对象的最近一级目录的`ctm.md`
  （对象不是工作目录中的一个路径时写在项目根目录，条目中写明对象；说它的话不属于任何工作时立即写）；统一标记，注明来源与时间。
  不立即写，是因为文件与对话是两条路：执行者开工就读文件，CTM的记忆写入在派发之后，同一项工作里紧接着的细化总比文件快一步
  （2026-11-24真实试用：“这次按url顺序调整”被误记为对象规则并立即写入；下一句把它限定为只调整新增部分，执行者读到的仍是旧条目，判为冲突停下来问用户）。`ctm.md`是CTM的记录：只留在本机（CTM写它时把它加进该仓库的本地忽略列表`.git/info/exclude`），执行者只读，不改、不提交。
  原因（2026-11-23真实试用）：一条被写进`ctm.md`的规则随一次提交进了公共仓库的PR，用户不得不纠正，并定下全局规则“ctm.md不提交”。
- 写进源码注释由CTM提议（在写入`ctm.md`的同时）：约束注释是代码的一部分，随代码进入版本库，同事和其他agent也读得到；但它是用户的代码，而“对象规则还是这次的改动”
  又常有出入（独立评判者之间也常不一致）。所以CTM把它作为带编号的待决事项提出（要把这条规则写进X的注释吗），用户回答后，
  提议和用户的原话一起交给那项工作的执行者：同意就写，不同意就不写。
- 一条对象约束被替换后（包括用户说它不再成立），CTM随即删去它在`ctm.md`里的条目（文件里只剩CTM的说明时删去文件），收回还没回答的注释提议；用户回应过把它写进注释的提议时，再提议更新注释。执行者读到的只有现行的规则；读过旧条目的执行者在下一次转话中得知它已被替换。
- 判断出错的代价因此不大：误记最常见的是把这次改动的细节当成规则，而用户接下来几句往往正是在细化同一个改动——它们在写入文件之前就替换了误记的规则；
  留下来的多记一条只在本机的`ctm.md`里，以后与要求冲突时让执行者停下问一次，用户一答即被替换；进入代码的注释要经用户同意。
  这比把判断调得更严更合适——两版更严的记忆说明（V10、V11）都把真正的长期规则一起漏掉了，而漏记的规则会被悄悄违反。
  对象约束靠对象所在的文件承载，说的是一个具体的对象。还没有文件的具体对象（一个正在规划的网站），约束先留在说它的那项工作上，有了工作目录后再写到对象旁；
  没有一个具体对象、说的是用户所有代码或所有工作的一类写法的（“函数名都加前缀”），不是对象约束，按用户的话的范围记为任务约束或全局约束——
  记成对象约束就没有地方承载，到不了任何执行者（MemoryCode长对话评估中这样的规则全部丢失）。
- 约束注释只能经由用户的决定修改，`ctm.md`只由CTM按记忆改写；执行者删改了它们，控制层从diff中发现后视为越界并升级。
- 对象被重构、拆分或删除时，执行者把约束注释随之迁移，或提请用户确认是否失效；`ctm.md`里写到的对象动了，执行者在答复中说明，条目由CTM更新。
- 新接触一个项目时根据项目已有的说明文件起草`ctm.md`条目：若要做，由CTM自己读这些文件、作为提议交给用户，不夹带给执行者（暂未做）。
- CTM在记忆中按对象建索引（用于查询、冲突检查、界面显示和`ctm.md`）。对象（“transport层”“计费那块”）由语义理解认出，不靠字面匹配。

**区分两者**：问“这条规则是否应在以后任何涉及这个对象的工作中继续成立，而不必再说”——是，则为对象约束（例如一份记忆文件的长期写法、一个测试本身的设计）；只针对这次的产出或这项工作的做法，则为任务约束（例如这次改动的格式、这一个PR的描述、这项调研的范围）。对排查方向和原因的判断是决定，不是约束。拿不准时先当任务约束；同一要求在不同任务中重复出现，
是CTM提议改为对象约束的信号。用户可以在界面上改变约束的种类或位置。
**两者冲突**：用户的话本身就在修改规则（“改为……”“不要再……”）时，这是用户的决定，记忆写入时替换旧规则，不问。任务里的要求与对象约束相反、而用户没有表明要改这条规则时，
由执行者在改文件时发现——它读到约束注释与`ctm.md`，也知道这次实际要改什么，比CTM在消息阶段猜测更准，也不必为每条消息多一次检查——执行者停下，经控制层作为需要用户决定的事上报，
CTM问用户是这项任务的例外，还是修改这条对象约束。

### 3.6 决定与文档

- **决定**是简短条目，来自用户或经用户采纳，分三类：定下的（批准的方案、选定的做法、对原因或方向的判断、对结果的认可）、被否定的（交给执行者时单列为“不要再用”）、
  被质疑的（用户质疑了agent的某个结论而没有否定它：交给执行者时标为“用户质疑过，使用前先核实”，之后被证实或否定时由新的决定替换）。新决定替换旧决定，旧的保留为历史。
  权威在决定条目上，文档只展开说明并引用决定编号。被别的任务引用的决定改变时，引用者待重核。
- **知识在文档里**：分析、设计、调查结论、机制和配置说明都写成文档，由后续执行不断更新，形成版本历史；不把细节拆成大量知识条目。
  每个版本连到产生它的执行、任务以及当时的决定。
- **种类**：知识文档（持续演进）、交付物（用户要的文档、邮件、评审意见，从草稿到定稿）、报告（一次调查或测试的结论，带时间，只追加不改写）、计划。
- **Agent行为指导**：Goal与Task面向用户的目标和产出，知识文档面向概念；行为指导是第三类：agent遇到某类概念、做某类操作时该怎么做（例如启动子进程的方式、搜索用什么工具），与skill同类。
  用户说出的这类普遍做法存为行为指导文档，带“何时用”的描述，交给执行者时给出索引、需要时自己读；它不进任务树。只针对某项工作的做法仍是这项工作的指导或约束：
  区别在于用户说的是这项工作该怎样做，还是这类操作在任何工作里都该怎样做；同一句话在不同情景下可能是两者之一，由CTM看情景判断。
  以后还要有工具、skill、MCP的清单，目前先只有行为指导文档。
- **写法**：区分已核实与未核实的说法，已核实的注明依据（命令输出、文件版本、测试）。
- **位置**：知识文档默认在CTM文档区；交付物在任务的工作目录里，即项目文档。
- **选哪份文档**：每份文档带一句“用途与何时用”的描述；CTM在初始context中给出相关文档的索引，执行者选择要更新的文档或提议新建，在答复中报告；同一份文档同一时刻只派给一个执行者修改。
- **增量更新**：知识文档按章节修改，不整篇改写，避免反复改写造成信息丢失。
- **过时**：决定被替换或文件变化后，引用它的章节标为过时，在下一次用到这份文档时一并更新，或在用户要求时更新。
- **工作目录是概念层的边界**：CTM只认工作目录及其中文件被观测到的版本；分支、提交等版本控制细节属于执行层面。
  同一工作目录同一时刻只派一个会修改它的执行者；需要并行修改时由执行层面提供隔离的工作目录，对CTM而言就是不同的工作目录。

### 3.7 文档浏览

任务树负责结构和纠正，文档浏览负责深入阅读。在树上选中节点即打开它的页面；查询答复的出处也链接到这里。

| 页面 | 内容 | 来源与编辑 |
|---|---|---|
| 任务元数据 | 目的与范围、工作目录、状态与历史、约束与决定、进度、关系、执行记录、相关文档 | 由记忆生成；在这里修改就是对树的修改 |
| 任务交流记录 | 这项任务相关的用户消息、CTM的转述与提问、每次执行的总结和最终答复 | 由已保存的记录生成，不另外维护，不可编辑；回顾工作来龙去脉看这里，执行者需要时也可以读 |
| 知识文档 | CTM文档区中的文档 | 有版本；可直接编辑，产生来源为用户的版本 |
| 项目文档 | 任务工作目录中的文档 | 即工作目录的当前内容；编辑等于修改工作目录中的文件 |

- 页面都由同一份记忆生成，界面只是视图。版本历史与差异可查看，过时章节、已核实与未核实的说法在页面上标出。
- 双向链接：文档 ↔ 用到或产出它的任务、引用的决定。
- 用户编辑的文档与树上的决定矛盾时，CTM把它当作用户的新表达，提出更新那条决定的建议。
- 用户正在看的页面、选中的段落是定位信号。

## 4. 时间

时间贯穿全图，回答四类问题：指的是哪一次、现在处于哪个阶段、当时知道什么与后来更正了什么、这条信息现在还能不能用。

- **记录**：发生时间、获知时间、有效区间（约束、决定）、观测时间与窗口（易变状态）、期限与事件条件、计划与实际、在途时长、最近活跃时间。
  日历时刻、耗时、媒体内位置、累计用量是不同的轴。
- **参照**：“刚才、昨天、上次、第一版、修复前”解析为具体的任务、尝试、版本或时段；重试和新一轮是不同的实例。
- **阶段与时机**：门控条件由事件触发，时间流逝不会自动完成、取消或解除暂停；在途操作完成前一直悬置。
- **更正与替换**：用户说出的约束、决定（含被否定的做法）与环境在写入时与同一范围内现行的条目比较，记下它替换了哪些（执行者的报告不替换它们；进度是带时间的当时状态，以最新的为准）；旧条目保留原有时间和“被谁替换”，不再作为现行条目交出。被否定的做法连同替代它的做法一起保存，交给同一工作线的执行者时单列为“不要再用”。
  用户也可以只**收回**一条已记下的东西——说它不对、不再需要，不给新的做法：记下用户的这句话（不再要什么），由替换一步让被收回的条目失效。记的时候方向不能弄反：用户要去掉一条规则，记成“已否定：去掉这条规则”，执行者读到的就是相反的要求（2026-11-24真实试用）。单设“撤回”一类试过（记忆V12）：提取一步看不到已记的条目，分不清收回已记的与一条新的否定要求，一次也没用上，反而少记了决定，没有采用。
- **适用**：约束、决定只看有效区间与替换，不随时间衰减；易变状态带观测时间和重读方法，不当作当前事实。
- **检索时的时间权重**：对全部候选连续加权，有底数；消息中有时间指称时改以所指时点为中心。

## 5. 运行

### 5.1 用户消息

CTM对每条消息要定的只有两件事：用户的话**送到哪里、以什么方式送**（哪个执行者的session、作为这项工作的内容还是旁问、新工作挂在树上哪里），
以及**记下什么**（以后还要用、原话会掉出窗口的约束、决定、事实、指导）。其余的判断属于别的角色：执行者读原话和现场自己理解要做什么，
控制层按合同把关不可逆的动作，对象约束由执行者在改文件时读到，结构的整理由维护完成。

1. **指向与对象**（一次轻量调用，不做归属决定）：判断消息用哪些方式指向它要说的工作（可多选），提取它说到的对象和时间指称；贴来的材料与用户的话分开。
   指向方式决定到哪里找候选：

   | 指向方式 | 候选从哪里来 |
   |---|---|
   | 回应刚展示的结果、方案或待决事项（批准、否定、纠正、追问、核验、回答澄清） | 最近展示的条目和待决事项所属的工作 |
   | 没有指向的推进、控制或状态询问（继续、停下、进度如何） | 当前工作（用户最后交流的那项）；运行中、等待中的执行者只作参照 |
   | 近指代（这个、它、刚才） | 最近10–20轮去过的工作 |
   | 点名工作、对象、产物或标识 | 对象→记忆中的对象→碰过它的工作，不论多久以前 |
   | 时间指称（昨天、上次、第一版） | 所指时点附近的工作，与对象检索的结果互相印证 |
   | 贴来的材料 | 材料中的对象→同上；运行中的工作 |
   | 引用别处定下的方案、结论 | 记忆中的现行决定（它们是用户说出的，作为对象带出所在的工作）；文档的索引以后再考虑 |
   | 新的要求 | 仍按其中的对象找相关的工作（它可能是某项工作的继续、一部分或下一步），当前工作线 |
   | 外部调研 | 查询列表中的调研条目，相关的工作 |
   | 寒暄 | 不需要候选 |

   对象写成消解指代后的明确描述；标识原样照抄，不纠正拼写。界面选择与显式引用（树上选中的节点、文档浏览中的页面和段落、@引用的对象）直接确定归属，不需要候选。
2. **候选**（代码）：按指向方式定各路的配额，取并集，不关闭任何一路（判错指向方式只多几个候选，不会漏掉正确的那一路）。对象这一路：
   消息中的对象与记忆中的对象比对——目前记忆中的对象是用户在以往消息里说到的对象（用户自己的说法，消息送达后挂到那项工作上）和各项工作改过的文件；
   标识完全相同或只差拼写错误（只对标识按字符比较），名称按embedding相似。配额按对象计：每个找到的对象带出碰过它的全部工作（一族工作，设上限），
   不在这里按分数或时间替LLM挑选其中一项。不用整条消息的向量：它混进了措辞和材料，找到的往往只是话题相近的工作。
   执行者产生的标识（PR号、分支、文档）是否也作为对象，以后再考虑。
3. **送达**（一次调用；候选都不合适、或要新建顶层工作需要查重时，扩大到全树再调一次）：候选按对象分组列出，看每项工作的现状（状态、最近结果、遗留问题、
   用户最近对它说的话、执行者在忙还是在等、之后做过的工作）和最近的对话，在同一对象的一族工作中排出最可能的几项，判断送到哪里、以什么方式送；
   排在后面的两三项作为备选显示给用户，选错时点一下即可改送。送达方式：原工作的session、新工作及其在树上的位置（它服务的Goal——已有的，或总结一个新的长期目标——以及在Goal下挂在哪里，3.4）、借用父任务的session、旁问（只读fork）、
   调研条目、对某个执行者的控制，或因为说不清而动作不可逆先问用户。只是对CTM说的话（要它记住的偏好与规则、对它或所有执行者以后做法的调整）不送给执行者，由第5步记下，答复中说明记下了什么（1.1）。新工作需要先规划时标出（3.4）。一条消息要送到几处时分开送。在对话中写明送到了哪里，用户一眼能看出并纠正。
4. **派发**（代码）：按送达的位置拼执行context（5.2），或把用户原话与新生效的条目转给原session；贴来的长材料存为文档，执行者拿到原文或读取位置。
5. **记忆**（在派发之后）：此时已知消息送到哪项工作。一次调用提取约束、决定（含被否定、被质疑的）、事实、指导和行为指导，定下各自的位置（3.5、3.6）；
   有新条目、且这条路径上与对象、全局范围内有现行条目时，再做一次聚焦的比对：每条新条目只和与它最相近的几条现行条目比，判断它替换了哪条、或只是重复（第4节）。比对时新旧条目都标明是否是被否定、被质疑的——被否定的做法与它所否定的要求字面上是矛盾的，不标明时，用户重申一条被执行者误解的规则，记下的“被否定：执行者的误解”会替换掉用户刚重申的规则。
   把替换放在提取之外，是因为一次调用里既要提取又要对照全部现行条目时，它随手配对，误判的替换多——误判会让一条仍然有效的要求被标为“不要再用”，
   代价大于漏判（漏判时两条都交给执行者，执行context按“越新的优先”处理）。
6. **答复**：在对话中说明安排，任务树同步显示。

### 5.2 执行

1. **形式**：分析类问题用单次调用；需要读写文件、运行命令的用subagent或session。
   **工作目录**由CTM按任务定，执行者就在那里运行：消息里说出的目录 ＞ 所属工作（上级或前一步）的目录 ＞ 按用户的话在他做过工作的目录中判断所属项目；不属于任何项目的工作（写文档、查资料、一般事务）在CTM自己的目录下有一个单独的临时目录。用户不需要预先指定工作目录。
2. **生命周期**：CTM判断这条消息是原任务的继续，就复用原任务的session；判断是新任务，就新建session。session通常没有结束状态，隔了多久都可以接着用；
   只有context接近上限、而用户不愿压缩时才结束。原任务已经做完、现场又被之后的任务改变了，用户再说“继续”时，多半是新任务：新建session，从现场重新开始，
   由执行者对照context中的原任务与之后各任务的结果自己判断现在的状况（CTM不记录它与原任务的关系）。两种判错的后果不同：误判为继续，执行者带着过时的现场工作；
   误判为新任务，丢掉原session中的细节，但新session有路径与兄弟的context——CTM结合情景权衡。
   复用session时，CTM转去：用户的原话、路径上尚未转达的约束、指导与决定、被替换或否定的做法、涉及的文件被别处修改的通知、在fork中回答过的查询结论。
   执行者的状态：工作中、等待（等用户或CTM）、空闲。
3. **初始context（CTM拼接，偏小）**：
   - 执行合同：**目标就是用户的原话**（一条消息涉及多项工作时，取属于这项任务的段，原文照录）；授权以原话为准，原话没说的沿用该任务此前的授权与仍有效的限制，
     不可逆动作只有用户明确要求时才授权。CTM不改写用户的话、不替用户补充要求、不自行收紧或放宽——评估中由CTM改写的合同使执行者的正确率明显下降，
     主要错误是捏造义务和过度收紧（评估进度阶段4）。固定条款：改文件前查看并遵守文件中的约束注释和路径上各级`ctm.md`，不得删改它们；缺信息先问CTM；
     答复简要说明做了什么、改了哪些文件、验证情况、未决问题、需要用户决定的事，长内容写进文档。规划者为一项计划步骤生成的合同另有完成标准与投入预算；
   - 任务现状：目的、工作目录与运行环境、阶段、进度与验证情况、待决事项、前置任务交来的结果；
   - 路径上的任务约束与决定（含根上的偏好与全局约束）；
   - 最近进度：最近几次执行的总结（含失败的尝试和原因）；**这项任务与其上级最近几轮交流的原文**——用户的话和执行者答复的结尾；
   - **最近执行过的兄弟任务（约7个）和上级任务最近执行过的兄弟（约3个）**：它们的结果、决定和最近的交流原文——它们构成这项任务所在的现场，数量大致对应人对周围工作能记住的范围；兄弟的约束和指导不带（约束挂在兄弟上就是为了隔离）；直接挂在根下的任务没有这样的兄弟；
   - **对话中最近几轮（约6轮）的原文**，不论属于哪项工作，并注明可能属于别的工作、只用来理解这条消息指的是什么、其中的要求只属于各自的工作——用户在一条对话里交替推进多项工作，新请求常直接接着刚在另一项工作里做完的东西（例如“把代码提交了”），按树组织的范围到不了那里（评估D块：所需信息完整在context里的比例由0.22升到0.44，缺失由0.38降到0.15，未见执行者照做别的工作的要求）；
   - Agent行为指导文档的索引；
   - 相关文档的路径和用途（执行者需要时自己读）；用户这次指到的内容；可询问的条目清单（相关决定、约束、文档的标题）。
   初始context只放这次工作明显需要的东西，按固定顺序组织（固定条款与长期不变的部分在前、本次变化的部分在后），便于模型缓存复用。
4. **执行控制层**：
   - 区分执行者停顿的类型：下一步在合同范围内、只是问要不要接着做的，直接让它继续；动手前请认可方向或方案、或请求有副作用和超出范围的动作的，按合同放行或升级；提出合同没要求的可选步骤或几个选项的，交CTM：用户原话、现行约束与决定、根上对用户的理解已经清楚给出答案时由CTM代答，否则问用户；需要信息的，交CTM；
   - 检查形式上的完成：要求的产出是否都有、答复是否符合约定、长内容是否写进文档；不满足时要求补齐；
   - 处理错误、重试、超时和预算；连续继续没有新进展或反复同一错误时停止并升级，由CTM决定重新规划、缩小范围或询问用户；
   - 执行者遇到不可逆或超出边界的动作时按合同放行，合同没覆盖的升级；发现删改约束注释时升级；
   - 长时间运行的执行在里程碑处报告简要进度，CTM随即写入任务进度，避免执行中断或context达到上限时丢失已完成的工作；
   - 只把这些交给CTM：需要记忆才能回答的询问、需要用户决定的事、授权之外的动作、里程碑进度、完成、失败。往返记录留在控制层作为证据。
   - 控制层只判断形式上的完成；做得对不对由CTM和用户判断。它不持有记忆。
5. **CTM与执行者之间（经控制层）**：

| 方向 | 内容 | 处理 |
|---|---|---|
| 执行者 → CTM | 询问：某个决定、约束、文件位置、别的任务的结果、历史做法 | CTM从记忆作答（只给当前有效的）；没有的说“不知道”或转问用户 |
| 执行者 → CTM | 请求：需要用户批准、选择或补充信息 | 作为待决事项转述给用户，答复后传回；执行者先做不受影响的部分，在答复中列出所作假设 |
| 执行者 → CTM | 完成、失败、受阻 | 写回并按通知规则转述 |
| CTM → 执行者 | 用户关于这项任务的新消息、别处新定的约束与决定 | 送入活跃session |
| CTM → 执行者 | 控制：暂停、停止、恢复、改变范围 | 控制层执行并报告已产生的影响 |

6. **结果处理**：答复和痕迹保存为Run的证据；CTM把答复简要总结后写入任务进度，文档与文件的新版本连到这次执行和任务；
   答复中的长篇内容存为文档。
   - 用户在环：CTM决定转述什么；用户对转述的反应决定哪些内容成为决定、被否方案或待决事项。
   - 自主推进的计划步骤：完成与否先由控制层按完成标准判断，CTM把结果交给后继和父任务。
   - 执行者自述与痕迹不符时以痕迹为准；转述时说明哪些有痕迹支持。

### 5.3 查询

只为了知道点什么、不要求产出也不改变资源状态的请求是查询：解释、查找、原因、现状、进度、“我们之前怎么定的”。
查询没有单独的入口：用户只在对话中说话，由CTM按段判定是查询还是任务，判定为查询的段，答复显示在查询面板。

0. **判定与纠正**：查询还是任务拿不准时按查询处理——查询只读、不改变任何东西，判错了用户一句“我是要你改”就能转为任务；反过来把查询当任务，可能做出用户没要的改动。CTM在对话中写明“作为查询回答”，用户可以随时改判。

1. **不建节点**：查询记录连到相关的工作；与任何工作无关的连到根。
2. **回答**：问的是已记录的事（做过什么、定了什么、说过什么、进度和结果）而记忆能完整回答的，由CTM直接回答；问文件、日志、运行状态、外部数据的现状，或要解释、分析、推理的，派发只读执行，记忆里的相关记录作为线索交给它——记录可能已过时或只是执行者未核实的说法，只拼凑以前的说法也答不好解释类问题（评估G块：原先记忆里找到就直接回答，凭记忆的回答约七成不完整或错误）。只读执行的合同禁止任何修改：问的是项目本身（代码、历史、做过的事）时，先在树中找相关的任务；
   相关任务有session时fork这个session来回答（它本来就了解这些，查询的过程也不进入它的执行context），否则新建只读执行者。答复较长时同样存为文档。
   查询只关联到它问的任务，回答记为查询的结果，不成为那项工作的内容或进度（否则那项工作看起来也在做这些分析，后面的消息会被误挂上去）。
   观察到的易变状态作为带观测时间的记录保存。
3. **展示**：完整答复显示在查询面板，条目带编号，出处链接到文档浏览；对话中给一两句结论和指向这条答复的链接，因此对话窗口里能看到查询的结论，后续“按第二条改”之类的指代也能落到面板中的条目上。同一条消息里的任务段照常在对话中答复。
4. **记录**：查询与答复保存为可检索的查询记录；现阶段不自动写入知识文档，也不自动生成Goal或Task。
5. **转为任务**：用户看了结果后要求产出或改动，才建立任务，初始context带上相关查询结果。回答需要改变状态才能得到时，CTM先问。

### 5.4 转述与通知

CTM写给用户的每条消息都是可指代的展示物：待决事项和选项带编号并标明所属任务，一次只让用户决定能分清的事。
需要用户决定、受阻、完成、与预期不符时进对话；其余进度只在任务树和执行视图更新。

### 5.5 界面修改

每类修改同步处理四方面：记忆关系（消息、约束、决定随之改挂）；运行中的执行者（受影响的收到更新，放弃的任务停止其执行者正在做的事，session保留，任务重新打开时接着用）；
待决事项（转移或撤销）；参照（作为以后定位和维护的依据，不变成硬规则）。

### 5.6 定期维护

读取上次维护以来写入记忆的消息段与进度及其归属（3.1中挂在节点上长期保存的Segment与Run总结，不是保留的对话；不只看节点列表）：合并重复任务、修正父子与先后关系、把同一项工作一步步提出的部分归到同一上级（用户说出过的目的建为Goal，否则建Task级上级）、把挂错的消息改挂到它实际属于的工作或从中拆出新节点（新工作被当作当前工作的继续送达、一串询问后来发展成一项工作时，节点里会混进别的工作；从这些消息写下的约束、决定、提及和当轮执行总结随之移动，已在执行的session不拆，之后的消息按新归属送达）、调整约束的位置（上移与回退，3.5）、修状态、改名；定期运行，另外对挂在根下、还说不出属于哪项工作的新节点，在又有几条相关记录写入后复查；这批记录只覆盖上次以来的工作，所以维护还回看已有的结构（3.4）：工作归到它服务的Goal下、同一个目标的Goal合并、同一项任务的几个部分归到一个上级任务下；整理文档（合并重复、拆分过大、标出过时）；
对象重构时迁移约束注释。用户改过的部分不锁定，但只有用户后来的话或操作与之矛盾时才直接改；仅凭CTM的推断只能提建议。

## 6. 规则

- **权威**：用户的消息和界面修改 ＞ CTM的推断 ＞ 定期维护。
- **规则优先**：这条消息中的明确要求 ＞ 任务约束与决定 ＞ 全局偏好与全局约束 ＞ CTM对用户的理解 ＞ 人格的默认做法。
  对象约束与任务要求冲突、而用户没有说要改规则时，执行者停下经控制层上报，由用户决定；整体目标不参与排序，不产生授权。
- **动作边界**：以用户这条消息为准；没说的，沿用该任务此前的授权和仍有效的限制，不自行收紧或放宽。
- **问还是做看可逆性**：本地改动有版本、可以撤回，按最可能的理解先做，在对话和树上标出理解；提交、推送、部署、删除、对外发送等
  不可逆或有外部影响的动作，理解不确定时先问。执行中才遇到的不可逆动作，由控制层按合同放行或升级。
- **提议不是授权**：规划者和执行者开出的工作只是提议；属于用户已授权范围的可以直接推进。
- **各自的事**：执行者只做用户的工作，只拿到用户的原话和context；CTM自己的事（记忆、`ctm.md`、提议）由CTM自己做，不夹带给执行者；对CTM说的话不送给执行者（1.1）。

## 7. 场景推演

每个场景按“消息 → 理解 → 写入 → 行动 → 执行context → 答复”推演，记录它支撑的设计。

**S1 查询与任务**。用户：“帮我看下X服务的Y告警为什么一直响。”用户要的是原因 → 查询，不建节点；记忆里没有答案，派发只读执行；
结果显示在查询面板，查询记录连到X服务相关的工作。用户接着说“那把它修好”，这才是任务（改变服务状态），初始context带上刚才的查询结果。
执行需要工作目录和运行环境，记忆里没有时CTM先问。→ 3.4判据、5.3。

**S2 并行时的短批准**。CTM刚转述了任务A的待批方案和任务B的结果。用户：“可以，开始吧。”
指向最近展示的待决事项；同一条转述里有两个待决事项时就含糊。→ 待决事项带编号和任务；短批准绑定最近一个明确提出的；
同时有多个时，可逆的按最近一个处理并说明，不可逆的先问（5.4、第6节）。

**S3 隔天回到旧工作**。用户：“昨天那个转写clear的改动接着做。”时间指称“昨天”＋对象“转写clear”→ 任务T。
T还没做完、期间现场没有大的变化，就是T的继续，复用它的session；T已经做完、之后的任务又改了相关代码，就是新任务，新建session，context带上T与之后各任务的结果，由执行者核对现场。
复用时CTM转去用户的话和T空闲期间路径上新定的约束与决定、被别处改动的文件、相关的查询结论；新建时连续性依赖写回质量。→ 5.2第2、3、6条。

**S4 纠偏**。CTM转述了T的实现结果。用户：“不对，transport不能暴露采样率参数。”这句话说的是模块本身的设计 → 对象约束，
CTM记下它，同时否定执行者的做法；T的session从对话中已经知道。别的工作的执行者进入这个目录之前，CTM把它写进transport模块目录的`ctm.md`，并提议把它写进transport入口文件的约束注释。T的session仍活跃，CTM把纠正转给它。
别的Goal下修改transport的工作改文件前会读到这条约束。→ 3.5。

**S5 委托规划与执行**。用户：“把X功能做完：先设计，再实现，测试通过后提PR。”CTM调用规划者，子任务以提议出现在树上；
用户批准后按依赖派发；“提PR”在原话里已授权，记在对应子任务上，门控为“测试通过”。执行者常在中途停下询问，
控制层按合同让它继续；进度只在树上更新，完成、受阻、超出授权的进对话。→ 5.2第4条、5.4。

**S6 核验报告**。CTM转述“T已完成，测试14个通过”。用户：“测试真的跑了吗？”这是查询：CTM查执行痕迹，有命令和输出就直接回答并给证据；
没有就派发一次只读核验。→ 5.2第6条、5.3。

**S7 依赖别的任务**。在写文档的任务B里，用户说“按我们定的方案写”。指向方式是引用别处的结论；记忆中的现行决定是候选来源之一，
A中用户批准的那条决定带出任务A；送达仍送到B，B的初始context只带这条决定，不带A的线程，并记一条跨任务引用。A的决定以后改变时，B待重核。→ 3.6、5.1。

**S8 查询后行动**。用户：“我们之前对采样率是怎么定的？”CTM在查询面板给出现行决定和被替换的历史，条目带编号。
用户接着说“按第二条改base_recognizer”：“第二条”解析到展示条目；选中的若是历史条目，就生成新的决定替换现行决定，并告知用户这是改回旧方案；
然后建立任务。→ 5.3、5.4。

**S9 用户改树**。用户把一条消息从T1拖到T2，并把T3合并到T1。由这条消息产生的约束和决定跟着改挂；T2若有运行中的执行者，收到更新；
合并时停止进展较少的执行者，其结果写回合并后的任务；修改作为以后维护的参照。→ 5.5。

**S10 外部变化**。用户手改了一个文件，部署状态也变了。CTM观测到改动，生成来源为用户的版本；部署状态作为带观测时间的记录。
正在运行、涉及该文件的执行者收到更新。→ 3.6、第4节。

**S11 指代含糊**。用户：“把那个配置改回去。”最近两项工作都改过配置。本地改动可逆：按最可能的理解做，写明“理解为T3的配置改回到某版本”，
并在树上标出；已推送或已部署的先问。→ 第6节。

**S12 打断执行**。用户：“先停一下那个部署。”指向方式是控制，候选来自当前与运行中的工作，送达判为对正在部署的那个执行者的控制；CTM经控制层停止或暂停它，
任务暂停并记录原因，如实告知已产生的外部影响。→ 5.1、5.2第5条。

**S13 一条消息涉及多项工作**。用户：“A先别合并；B的文档按新方案改；另外查一下C的告警。”送达把它分成三份分别送：
对A的控制，交给B的工作内容（“新方案”由记忆中B的现行决定说明），关于C的旁问；记忆只记下“A暂不合并”这条决定。答复按工作分组，每组可单独指代。→ 5.1。

**S14 浏览中指出问题**。用户在文档浏览中选中设计文档的一段：“这里说的不对，应该是先commit再flush。”
定位信号是正在看的段落；这是对设计的纠正，形成新的决定替换旧决定，文档章节标为待更新，并提议在下一次相关执行中改写。→ 3.6、3.7。

**S15 偏好与对用户的理解**。用户：“以后回复先给结论。”这是用户明确的偏好，写到根上，立即生效。
用户说“全局记住：ctm.md不要提交”也是这一类：话是对CTM说的，CTM记为根上的全局约束，答复中说明记下了什么，不送给任何执行者——送给执行者，执行者会把“记住”当成一件工作去做，改它自己的配置文件（2026-11-23真实试用中发生过）。
另一方面，CTM注意到用户多次把执行范围收窄，形成一条对用户的理解“偏好最小改动”，作为推断记录依据，用于把以后的合同范围写准，
但不压过用户在某次明确要求的大范围改动。→ 3.3、第6节。

## 8. 设计结论

| 问题 | 结论 | 依据 |
|---|---|---|
| CTM的角色 | 用户唯一对话的助手；管理执行者、维护记忆、回答查询、转述结果 | 1.1 |
| 对话 | 一条连续对话，只保留最近窗口；长期记忆在树和文档里，消息当时写入，不压缩对话；待决事项必须进树 | 1.2、S2 |
| 送达 | 每条消息只定送到哪里、以什么方式送，以及记下什么；按指向方式从最近的工作、当前与运行中的工作、对象（用户说过的对象、改过的文件、现行决定）、时间取候选，由一次调用在对象的一族工作中排序选择；界面选择与显式引用直接确定；没有指向的推进、控制与状态询问归当前任务 | 1.2、5.1、S2、S7、S11、S12、S14 |
| 任务与查询 | Goal／Task必须有明确产出或改变资源状态；查询不建节点、只读执行、记录连到相关节点；没说明为哪项工作服务的调研记在查询列表里，结论写成文档，可继续、可被引用、以后可挂进树；查询在对话中提出，由CTM判定，答复显示在没有输入框的查询面板，对话里给结论与链接；拿不准时按查询处理 | 3.4、5.3、S1 |
| 树的层次 | 根（全局层）→ Goal → Task → subTask；Goal是长期目标（用户说出的，或CTM从请求总结、标为CTM总结，用户可改），以后同一目的的工作继续挂在它下面，不是项目或工作目录；每个Task都在某个Goal下；Task与子任务是包含关系（子任务都完成父任务才完成），兄弟是并列部分或先后步骤，拆不拆、怎样拆看情况；执行后的收尾是工作的继续，不建节点；工作目录是判断同一任务、组成部分的重要参考，不是边界；新建任务时就考虑它的Goal和它与最近工作的关系，并定期回看已有的结构；上级任务按一项具体工作归组，不按阶段或领域；用约束的后果检查挂载；当前任务不是新工作的默认上级 | 3.3、3.4 |
| 根节点 | 人格与对用户的理解只给CTM；整体目标只用于理解与建议；偏好与全局约束向下继承 | 3.3、S15 |
| 任务内容 | 目标与范围、约束与决定、进度；知识在文档里 | 3.4、3.6 |
| 约束 | 任务约束在树节点上向下传递，拿不准放低；对象约束是对象文件中的注释或路径上各级`ctm.md`的条目（最近的优先），没有注释就没有约束；`ctm.md`由CTM写（在需要从文件读到它的执行者开始之前），注释由CTM提议、用户同意后由执行者写 | 3.5、S4 |
| 各自的事 | 用户的工作给执行者，只带用户的原话和context；CTM自己的事（记忆、`ctm.md`、提议）和对CTM说的话由CTM自己处理 | 1.1、第6节、S15 |
| 决定与文档 | 决定是权威的简短条目；Agent行为指导是第三类知识（与skill同类），存为带“何时用”的文档；文档分种类、有版本、区分已核实与未核实、引用决定编号、同一时刻一个写者、过时用时再改 | 3.6、S7、S14 |
| 工作目录 | 概念层只认工作目录与文件版本；分支等属于执行层面；同一工作目录同一时刻一个修改者 | 3.6 |
| 执行 | 判为原任务的继续就复用它的session，判为新任务就新建（原任务做完且现场已变时多半是新任务）；session通常不结束；查询fork session回答；新执行者的初始context偏小（路径、最近执行过的兄弟、对话最近几轮原文），缺什么由执行者询问；合同以用户原话为目标，不改写、不加要求；附工作线最近交流的原文 | 5.2、S3；评估阶段4 |
| 执行控制层 | 按合同驱动到完成；授权内的停顿直接继续；只把需要记忆、用户决定、越界、完成、失败交给CTM | 5.2、S5 |
| 结果 | CTM总结写入进度；长内容进文档；用户在环时由用户反应决定记住什么；痕迹优先于自述 | 5.2、S6 |
| 界面修改 | 用户权威；四方面传播；不锁定，但只有用户后来的依据才直接改 | 5.5、5.6、S9 |
| 动作边界 | 以本条消息为准，否则沿用任务授权；问还是做看可逆性；不可逆动作在执行时由控制层把关 | 第6节、S11 |
| 时间 | 约束不衰减；易变状态带观测时间；时间指称解析为具体实例 | 第4节 |

## 9. 推理无法确定、需要验证的问题

1. **用户习惯前提（1.4）**：没有会话上下文时，用户怎样指明工作。
2. **理解**：定位与指代解析的准确率，区分查询与任务、判断约束种类与位置的准确率，特别是S2、S11这类含糊处。
3. **执行**：偏小的初始context加按需询问能否让执行者做对；执行者会不会遵守约束注释、该问不问。
4. **控制层**：区分程序性停顿与实质问题的准确率。
5. **转述**：用户因转述不全而追问或纠正的比例。
6. **纠正负担**：用户需要改树的频率，以及改动后同类错误是否减少。
7. **成本**：每条用户消息、每次执行、每个查询的模型调用与token。

验证的方法见[目标与方法](goals-and-method.zh-CN.md)：测试数据必须符合目标场景（用户面对一个助手、没有session），不能直接拿session内的历史记录当测试。


## 10. 未来方向（尚未设计）

CTM是私人助理：经过一段磨合，它的context自动与用户的工作目标对齐，并调动多个运行环境完成任务。为此模型要在工作树与对象两条轴之外，
再加三条轴：**资源**（仓库、机器、远程主机、集群、服务，有身份、状态、规则与权限属性，与工作双向关联）、**反馈**（用户的纠正与批准归因到判断，
巩固为对用户的理解、带作用范围的偏好、做事的方法与长期授权）、**非消息输入**（时间与事件，和消息一样先判断属于哪项工作）。
这些都还没有设计；需要的底层能力与先后顺序见[目标与方法](goals-and-method.zh-CN.md)第6节。设计时仍守第6节的规则：用户的话为准、按可逆性问或做、
不替用户创造义务、执行者只拿到少而够用的context。
