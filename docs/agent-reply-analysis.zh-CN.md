# Agent回复分析

> 用途：说明执行agent的回复里有什么、哪些内容真正被用户和后续工作用到，是[CTM概念模型](ctm-concept-model.zh-CN.md)中
> 结果处理（5.2第6条）、输出约定和文档设计的依据。数据来自session内的历史记录；私有数据在 `research/agent-reply-analysis-01/`，
> 这里只给汇总和匿名化转述。

## 1. 方法

- 数据：15,031个用户轮次的agent最终回复（不含工具输出），来自415个会话。回复长度中位约800字符，
  90%分位约2,900字符；40%带标题或表格；工具调用中位3次，90%分位19次。
- 开放编码：80条回复（每会话最多3条），模型自由命名信息单元并说明以后谁需要它；再归纳出15类与属性维度。
- 定标标注：另取400条回复（226个会话，与开放集不重叠），拆出2,633个信息单元，标注类型、位置、核实程度、执行阶段、
  有效性、时效性、保留期限，并对照之后3条用户消息判断是否被引用、采纳、纠正或追问。
- 长程需要：对78道长程状态问题，逐条判断参考答案的信息来自用户消息还是agent回复，来自回复的哪一类、哪个位置。

## 3. 以后需要什么

78道长程状态问题共有313个信息来源：46%来自用户消息（要求66、纠正46、决定22），54%来自agent回复。
来自回复的部分：技术机制44、变更记录34、约束复述32、方案12、纠正11、配置规则10、验证8、状态快照7、决策5、定位5。
它们在回复中的位置分散（开头63、中间56、结尾51），且只有30%被用户明确采纳过。

## 4. 下一条用户消息和下一轮执行实际用到什么

第2、3节只说明回复里有什么，不说明谁会用。用户不会在意回复里的每个细节，执行者也不会逐条遵守。
因此对372对“回复 → 下一条用户消息 → 下一轮agent回复”，按实际发生的后续判断上一条回复中哪些内容真正被用到：

- **理解用户意图**：85%的下一条用户消息依赖上一条回复，但平均只依赖其中约1.2处内容。
  作用：指代对象142、被追问的内容124、被否定或纠正的说法71、被核验的结果或状态42、被批准或选择的方案37、agent提问的答案对象16。
  涉及的类型以技术机制103、方案60、变更45、目标范围41、诊断33、配置29为主。
- **执行下一条请求**（下一轮agent的工作或为它定计划）：平均需要约2.5处内容，约一半是必须的。
  作用：技术结论或机制276、文件与代码位置128、待执行的方案或步骤111、已完成的结果110、配置与参数105、验证状态102、未决问题59。
- **没用到的内容**：56%的回复中大部分或几乎全部内容对这两者都没用，另有24%约一半没用。
  典型的是过程播报、对目标的复述、未被采纳的推测、行号级细节、概念解释。

## 5. 结论

1. **回复的大部分对后续没用**：56%的回复中大部分或几乎全部内容既不用于理解用户的下一条消息，也不用于下一轮执行。
   过程播报、对目标的复述、没人接的推测、行号级细节、概念解释最常见。
2. **用户在意的是被他指到的那一两处**：85%的下一条消息依赖上一条回复，但平均只依赖约1.2处，多为指代、追问、否定、核验、批准。
3. **继续工作需要的是少量要点**：平均约2.5处，主要是技术结论、文件与代码位置、待执行步骤、已完成结果、配置、验证状态、未决问题。
4. **用户纠正的主要对象**是agent的方案、机制说法、诊断和配置规则；**61%的说法没有可见证据**，工具调用多不等于已核实。
5. **长期有价值的知识**（机制、规则、设计结论）分布在回复中间，适合沉淀在可演进的文档里，而不是拆成大量条目或留在对话中。

## 6. 在CTM中的处理

| 环节 | 处理 |
|---|---|
| 输出约定（写在执行合同里） | 长内容写进文档；给CTM的答复只含简要结果：做了什么、更新了哪些文档和文件、验证情况、未决问题、需要用户决定的事 |
| 答复到达 | 原文和痕迹保存为执行证据；CTM写一条简要总结进任务进度；答复中仍有长篇内容时存为文档 |
| 转述给用户 | 只转述需要用户知道或决定的：完成、受阻、与预期不符、待决事项；条目带编号以便指代；说明哪些结论有痕迹支持 |
| 用户的反应 | 落到被指到的条目上：批准成为决定，否定成为被否方案并记下新说法，追问成为待决事项 |
| 其余细节 | 留在文档和执行证据中，需要时检索或由执行者自己读 |

## 7. 原型上的对比（两条轨迹前140轮，私有数据汇总；早于当前概念模型）

| 写回方式 | 每轮模型调用 | 每轮输入token | 每轮输出token | 长程细节问题（可比的5个检查点15题） |
|---|---:|---:|---:|---|
| 回复到达即把内容全量拆成知识条目（早期方案） | 3.1 | 1.1–1.7万 | 约1300 | 12对2部分对，与研究版G2相同 |
| 只保留用户所指与继续工作所需的要点 | 2.2 | 0.9–1.2万 | 约800 | 9对5部分对 |

6个检查点18题上：完整历史17对，G2 15对，只保留要点9–11对（同一答案两次评分相差2题）。把工作要点也建成可检索的知识条目，没有改变结果。
只保留要点的方式少用约三成维护成本；丢掉的主要是已经定下来的接口和配置细节（例如某接口不接受采样率参数、两个环境配置都不新增某字段），
大多被判为“部分对”而不是答错。长程细节问题由模型生成，偏重细节，而且这组对比用的是session内历史回放。在当前设计中，这类已定下来的接口和配置细节应当成为对象约束或文档中的内容（见概念模型3.5、3.6），而不依赖从回复中提取。
